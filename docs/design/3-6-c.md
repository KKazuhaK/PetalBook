# 3.6 step (c): audit categories, scopes, view as a person, organisations people create

Status: plan, 2026-11-26, on main f9a5c65. Nothing here is built.

Step (c) of the approved build order (3.6 foundations) has seven items:

1. **Audit log categories**, filters and retention.
2. **Organisations people create themselves**, behind a site setting.
3. **Defaults**: 3 spaces per person, and what a new organisation starts with.
4. **The tenant detail page** for site administrators.
5. **Manage as this tenant's administrator**: the shared console in one tenant's scope.
6. **View as a person**: read-only, audited, never personal spaces.
7. **Dual-role scope selector**. PROPOSAL, waiting for the owner. It is its own
   last PR, so it can be dropped without touching the rest.

Owner decisions this plan implements (2026-11-23 to 2026-11-26, see the build
order and `decisions-2026-11-24.md`):

- Core audit is always on: sign-in and security, administration, permissions,
  deletions, exports and views. Optional categories are layered settings, site
  then tenant, default or forced: page reads, downloads, successful sign-ins and
  API calls.
- Retention is "older than X days" and/or "more than Y rows", joined by OR or
  AND. Core audit keeps a floor, so it cannot be wiped in one go.
- View as a person works like Canvas's student view. It has a banner, is audited
  every time, and is read only. It never shows personal spaces, drafts, tokens,
  sessions or connected accounts. A tenant administrator sees only their own
  organisation's spaces.
- Organisations people create follow Notion. A site switch, default **off**.
  3 per person. The hourly cap exists but is not used by default.
- Spaces per person default to **3** (was 20).
- One admin console for every scope. "Manage as tenant admin" renders exactly
  the tenant-scoped pages. Every admin UI change is checked as `admin` and as
  `acme-admin`.
- Every setting is layered (allow / restrict / lock, per-tenant rules). Nothing
  is a site-only on/off unless it says why (`ServerWide`).

Pre-release: one baseline schema per dialect, edited in place. There are no
migrations, and dev and demo databases are recreated.

## 1. Audit log categories, filters, retention

### 1.1 Today

- One table, `audit_log` (`internal/store/schema.sql:691-712`). Its ids sort by
  time, and it has indexes on `kind`, `user_id`, `tenant_id` and
  `(tenant_id, kind)`, plus `actor` without `id`.
- Writers:
  - The queue in `internal/auth/audit.go:45`: 10k rows, batched every second,
    dropped and counted when the queue is full.
  - `notify.WithAudit` (`internal/notify/notify.go:48`): the audit row and the
    notifications in one transaction.
  - `server.audit` and `server.auditRow` (`internal/api/tokens.go:376`,
    `internal/api/recycle.go:232`).
- About 70 kinds are bare strings spread across `internal/auth`, `internal/api`
  and `internal/spaces`. `store.SiteAuditKinds` (`internal/store/signin.go:377`)
  is a hand-kept list of the kinds a tenant administrator may not see.
- Retention is hard-coded: 100,000 rows or 90 days (`internal/auth/audit.go:14-20`).
  `TrimAudit` deletes by id range (`signin.go:470`).
- `GET /api/admin/audit` (`internal/api/signin.go:81`, `:518`) filters by `kind`
  and `user` only. The web page has a kind select and a username box
  (`web/src/components/admin/AuditSection.tsx:55`). Its hand-kept kind list
  (`:20-40`) has already drifted.
- `GET /api/admin/audit/download` and `features.auditDownload` are documented
  (`docs/api.md:9874`) and registered (`internal/settings/registry.go:257`), but
  not built.

### 1.2 Target

- **One registry of audit kinds**, in a new package `internal/auditlog`. Each kind
  is registered once, with:
  - its category;
  - its visibility (`site`: only the server's administrators see it; `tenant`:
    the tenant's administrators see it too);
  - whether it is core.

  A source-scan test fails when an audit row names an unregistered kind.
  `SiteAuditKinds` and the web's kind list are derived from the registry. This
  also delivers the "one table of audit kinds" of consolidation item 6.
- **Categories.** Core categories can never be turned off:
  - `security`: sign-in failures, lockouts, passkeys, identities, ended
    sessions, security settings, providers, secrets;
  - `admin`: settings, rules, plans, people, invites, groups, roles, tenants,
    tokens and grants;
  - `data`: deleting, restoring, purging, exporting, taking over and
    transferring spaces, space views, view as a person, opening a page in
    a view;
  - `system`: dropped rows.

  Optional categories:
  - `signins`: successful sign-ins (`login`). Default **on**: it is cheap, and
    today it is always written.
  - `reads`: a member opening a page or file. Default off.
  - `downloads`: attachments and file downloads. Default off. Exports are core.
  - `api`: token and MCP calls. Default off.
- **Visibility change.** Rows about one tenant are shown to that tenant's
  administrators, including those a site administrator wrote in that tenant
  (`tenant_changed`, rules, plan). Only the server's own kinds stay site-only:
  providers, mail, security, rate limits, lockouts, `dropped`. This follows
  "the tenant admin sees the site admin's changes to this tenant"
  (`phase-3-autonomy-and-providers.md:156`).
- **Retention** (one table, so site only, `ServerWide`):

  ```
  keep = rows younger than keepDays  [OR|AND]  the newest keepRows rows
  ```

  Rows outside `keep` are deleted, with one exception: a core row younger than
  the floor (90 days, a constant) is never deleted. Optional categories have
  their own `optionalKeepDays`, which is shorter.
- **Filters**: category (several), kind, person the row is about, actor,
  capacity, date range, and tenant (site scope). The date range is turned into
  an id range, because ids start with the time in milliseconds. No index on
  `at` is needed.
- **Download**: CSV of the current filter, streamed in pages of 1,000, at most
  100,000 rows per download. Audited as `audit_downloaded` (core, `data`).

### 1.3 Data shape

```sql
ALTER audit_log (baseline):
  category TEXT COLLATE "C" NOT NULL DEFAULT 'admin'  -- written from the registry at insert
  capacity TEXT COLLATE "C" NOT NULL DEFAULT ''       -- '', site_admin, tenant_admin (section 5)
CREATE INDEX audit_log_tenant_cat ON audit_log(tenant_id, category, id);
CREATE INDEX audit_log_cat        ON audit_log(category, id);   -- trim of optional rows, site filter
-- audit_log_actor becomes (actor, id): an actor filter pages by id.
```

`category` is stored, not computed when the log is read:

- the filter and the trim use the index;
- a kind that later moves to another category keeps the rows' old category,
  which is the true record.

Reserved ahead, so the shape does not change again:

- `capacity` (section 5, and section 7 if accepted).
- Kinds and categories for (d): `sso_*`, `domain_*`, `join_*` in `security` or
  `admin`.
- Kinds for IdP group mapping (`groups_synced` exists, `admin`) and for 3.7
  (`org_joined`, `org_left`, `context_switched`; switching is `signins`).

`database.md:223` planned a separate `activity_log` for high-frequency events.
This plan uses the same table instead:

- a category column plus a separate retention for optional rows gives the same
  cost;
- it keeps one reader, one writer and one UI.

Settings (registered in `registry.go`, layered):

| Key | Kind | Layers | Default |
|---|---|---|---|
| `audit.signins`, `audit.reads`, `audit.downloads`, `audit.api` | Bool | Site, Tenant | true, false, false, false |
| `audit.keepDays` | Limit, min 90 | Site (`ServerWide`: one table) | 90 |
| `audit.keepRows` | Limit | Site | 100,000 |
| `audit.keepMode` | Choice `or` \| `and` | Site | `or` |
| `audit.optionalKeepDays` | Limit 1–90 | Site | 30 |

Core categories have no setting. The registry refuses one.

`docs/api.md`: the "Audit log" section (`:770`) becomes one table of kinds with

### 1.5 Web

- `AuditSection` gets a filter bar: category chips, a kind select grouped by
  category, a person picker (the shared picker of the "add" flows, falling back
  to a username box until that lands), and a date range. Filters live in the
  URL query, so a link reproduces the view. A Download button sits beside the
  filters.
- The settings page shows the optional categories in their own "Audit" group.
  Retention shows in site scope only.
- Phone (below 640px): filters collapse into one "Filters" button that opens a

### 1.6 Cost

- **Insert**: one extra map lookup per row.
- **Optional categories**: they cost nothing while off (one settings snapshot
  read per event). When on, `reads` and `downloads` are deduplicated in memory
  per (person, page or path, hour). This reuses the bounded `firstOpen` table of
  `adminview.go:108`.
- **Queue pressure**: past 80% full, optional events are dropped first, so core
  rows are never crowded out. Their drop count goes into the `dropped` row.
- **Trim**:
  - the daily sweep runs at most three range deletes by primary key or
    `(category, id)`, in batches of `AuditTrimBatch`;
  - the cut for `keepRows` is one `ORDER BY id DESC LIMIT 1 OFFSET n` on the
    primary key.
- **Listing**: every filter combination pages on an index ending in `id`.
  Add EXPLAIN tests on both databases for tenant+category, actor and the date
  range.

## 2. Organisations people create themselves

### 2.1 Today

- Only a site administrator creates tenants (`POST /api/admin/tenants`,
  `internal/api/tenants.go:179`, behind `features.tenancy`).
- Registration (`internal/auth/emailflows.go:186` `Register`, `:424`
  `RegisterConfirm`) always makes a `member` of an existing tenant (`:452`). The
  tenant comes from `?tenant=` (`internal/api/mailapi.go:21-23`).
- `registrations.tenant_id` is a foreign key (`schema.sql:785`), so a pending
  registration cannot point at a tenant that does not exist yet.
- `tenants` does not record who made a tenant or how (`schema.sql:34`).

### 2.2 Target

On the registration page, when the site allows it, there is a second choice:
"Create my own organisation". It asks for the organisation's name and slug. The
slug is suggested from the name and can be edited.

The flow:

1. `POST /api/register` checks everything it checks today. It also checks:
   - the switch;
   - `features.tenancy` and mail;
   - the slug: format, and not taken by a tenant or a pending registration;
   - the caps.

   It always answers `202`, as today. The exception is a taken slug, which
   answers `409 slug_taken` before any address is looked at. Slugs are public
   (sign-in `?tenant=`), so this leaks nothing.
2. The confirmation link makes everything in **one transaction**:
   - the tenant, with `origin='self'` and `created_by`;
   - the person, as the tenant's administrator (`role=admin`, never a site
     administrator);
   - their personal space, as registration does today;
   - the plan from `orgCreation.plan`.

   If the slug was taken in the meantime, a numeric suffix is added and the
   welcome page says so.
3. Audited as `tenant_created` (`admin`, tenant-visible) with
   `detail.origin=self`.
4. Caps:
   - `orgCreation.perPerson`: counts the tenants this person created that still
     exist, through an index on `created_by`;
   - `orgCreation.perHour`: site-wide, default **unset**, through the shared
     `internal/ratelimit`;
   - the existing hard cap `store.MaxTenants`.

   When a cap is hit, the answer is still `202`, and the mail says no
   organisation was made, as `phase-3-autonomy-and-providers.md:571` decided.
5. In 3.6 an address has one account. An address that already has one gets the
   usual "you already have an account" mail. Creating an organisation while
   signed in is 3.7 (`POST /api/orgs`, reserved, built on the same
   `createTenant` helper).

Reserved for (d): the hook `orgCreationBlocked(domain)` returns nil until (d)
builds `restrictOrgs` on verified domains. (d) then makes it answer
`409 domain_managed` with the organisation that owns the domain and its ways to
join.

### 2.3 Data shape

```sql
tenants:        + origin     TEXT COLLATE "C" NOT NULL DEFAULT 'admin' CHECK (origin IN ('default','admin','self'))
                + created_by TEXT COLLATE "C" NOT NULL DEFAULT ''   -- user id; not a foreign key (outlives the person)
CREATE INDEX tenants_created_by ON tenants(created_by) WHERE created_by <> '';
registrations:  + org_name TEXT COLLATE "C" NOT NULL DEFAULT ''
                + org_slug TEXT COLLATE "C" NOT NULL DEFAULT ''
CREATE UNIQUE INDEX registrations_org_slug ON registrations(org_slug) WHERE org_slug <> '';
-- tenant_id of an org registration is the default tenant (it keeps the foreign key); org_slug <> '' marks it.
```

Settings, all site-level with a `ServerWide` reason ("a tenant does not exist
yet; creating one takes the site's resources"):

| Key | Kind | Default |
|---|---|---|
| `features.orgCreation` | Bool | false |
| `orgCreation.perPerson` | Limit 0–100 | 3 |
| `orgCreation.perHour` | Limit, nullable | null (unused) |
| `orgCreation.plan` | Text (plan slug, checked against `plans`) | `""` (no plan) |

## 3. Defaults

- `quota.spacesPerPerson` default goes from 20 to **3** (`registry.go:203`).
- A new tenant, made by an administrator or by a person, **copies no settings**.
  It has no tenant-layer rows, so it follows the site defaults. A later change
  of a site default reaches it, and nothing gets stale. What it starts with:
  - `origin` and `created_by`;
  - a plan: `orgCreation.plan` for one a person made, or the one picked in the
    admin create dialog (default none);
  - registration closed (`features.registration` default false, already);
  - its first administrator, through an invite (admin) or the registration (self);
  - that administrator's personal space.

  It gets no shared space. Onboarding suggests making one.
- Tests that assume 20 spaces per person are updated in the same PR.

## 5. Manage as this tenant's administrator (acting scope)

### 5.1 Today

- A route outside spaces checks its key in the caller's **own** tenant
  (`internal/api/routes.go` `handle`, the `allow(c, key, c.p.User.TenantID)`
  call).
- Lists take `?tenant=` to narrow a site administrator's scope
  (`internal/api/scope.go:30`). There are 13 callers of `adminScope`.
- Elsewhere the handlers decide the scope themselves:
  - 22 places use `store.AdminScopeOf(c.user())`;
  - 22 places use `c.user().TenantID`.

  So a site administrator cannot act in another tenant uniformly, and their
  site keys apply everywhere. For example, personal spaces show up
  (`site.spaces.personal.meta`), and tenant features do not bind them
  (`authz.Decide`, `subject.go:178`).
- The web console chooses its pages with `navFor(site)`
  (`web/src/components/admin/adminNav.tsx`), from `acrossSite(user)`.

### 5.2 Target

The console has a **scope**: the whole site, or one tenant. In tenant scope a
site administrator acts **exactly as that tenant's administrator** would:

- only tenant keys apply: `Subject.In(t) ∩ OfScope(Tenant)`. Site keys are set
  aside for the request;
- tenant features bind them (`403 feature_off`), as they bind the tenant's
  administrator;
- personal spaces are invisible: `site.spaces.personal.*` are site keys;
- accounts that hold site keys are out of reach, as they are for a tenant
  administrator;
- the site's rules and locks on the tenant are read only in tenant scope. They
  are changed on the tenant detail page, in site scope.

Wire format: the request header `PetalBook-Scope: tenant:<id>`. The console's
API client sends it on admin calls while in tenant scope, and only from that
browser tab. A header, not a query parameter, because:

- it is one value for every call, and needs no change to the ~60 URL builders;
- it never lands in a link or a log line;
- it differs per tab.

`?tenant=` stays as the site scope's list filter. Inside tenant scope a
`?tenant=` or `{tenant}` of another tenant answers `404`, as it would for that
tenant's administrator.

On the server:

1. `handle` parses the header once into `c.scope = {tenant, capacity}`. It
   requires `tenant.settings.read` in that tenant: a site administrator, or that
   tenant's administrator. Otherwise it answers `404 not_found` and never falls
   back to the site scope.
2. `c.p` is shallow-copied with the narrowed `Access`.
3. `c.tenant()`, `c.adminScope()` and `c.ownScope()` replace every
   `c.user().TenantID` and `store.AdminScopeOf(c.user())` in handlers. A
   source-scan test forbids those two forms outside `scope.go`.
4. `allow` checks in `c.tenant()`.

**Capacity.** Every audit row written in a request records `capacity`:

| Value | When |
|---|---|
| `site_admin` | a site administrator in tenant scope, or in site scope |
| `tenant_admin` | a key held in that tenant: built-in role, custom role, group grant, and from 3.7 a membership |
| `''` | no administration: sign-ins, a person's own account |

The rows carry the tenant, so the tenant's administrators see a site
administrator's actions in their audit, marked as a site action.

Opening a tenant scope writes `tenant_console_opened` (`admin`, core,
tenant-visible), at most once an hour per session and tenant (the bounded
`firstOpen` table). It needs no reason, because it opens no content. Every write
inside the scope is audited by its own row anyway. See open question 2.

`sessions.current_tenant` (`schema.sql:155`, reserved for 3.7) is the person's
**app** context and stays separate. The console scope is per tab and per request.

### 5.3 Web

- The console header gets a scope control: "Whole site", then the person's own
  tenant, then "Other tenant…" for site administrators. "Other tenant…" is a
  searchable picker over `GET /api/admin/tenants?q=`; with thousands of tenants

- In tenant scope:
  - the navigation is `navFor('tenant')`, the same pages a tenant administrator

  - a thin bar under the header says "Managing <tenant> as its administrator ·

  - the scope is in the URL (`/admin/t/<id>/<section>/<tab>`), so reload, links
    and the back button keep it.
- The site's tenant detail page and the tenant list link into

- Phone: the scope control moves into the admin drawer's header, and the bar

### 5.4 Cost

- One header parse.
- One 64-bit set intersection per request (`authz.Set` is a bit set).
- The narrowed subject is never stored.
- No extra query: the tenant check is a cached settings or tenants read
  (`TenantRefOf`).

## 6. View as a person

### 6.1 Today

- The person page has a disabled "View as" button
  (`web/src/components/admin/users/PersonPage.tsx:102-112`).
- What exists is the **space view** (`internal/api/adminview.go`):
  - an administrator opens a one-hour, audited, read-only view of one space
    (`POST /api/admin/spaces/{space}/view`, `routes.go:230`, key
    `tenant.data.view`, feature `features.adminView`);
  - views are kept in a bounded in-memory map per session (`:26-60`);
  - page opens are audited, deduplicated per hour (`:108`).
- `getPage` returns the caller's draft (`internal/api/pages.go:256`).

### 6.2 Target

An administrator opens the app **as a given person sees it**, read only, in a
separate browser tab. They see the person's home, space switcher, folders,
pages, search, tags, backlinks and history, limited to what this section allows.

**Rule: view as a person never shows content the viewer could not already open
with an audited space view.** It is a lens over the existing reach, not a new
reach. Concretely:

- **Which spaces:** the person's memberships (own and through groups), with
  their effective permission cut down to read. A space is shown only if it is:
  - in the viewer's admin scope;
  - not personal (**no personal space, of anyone, for any viewer**; a site
    administrator who must read one uses the separate, built-in-only
    `site.spaces.personal.content` view);
  - in a tenant that is not disabled.

  The space list says "N spaces hidden (personal, or outside your organisation)".
- **Who can be viewed as:**
  - someone in the viewer's admin scope. A tenant administrator can view only
    people of their own tenant;
  - never oneself;
  - never an account that holds site keys, unless the viewer holds
    `site.admins.manage`.
- **Excluded:** drafts, notifications, favourites and prefs, the account page,
  emails, passkeys, tokens, grants, sessions, connected accounts, the admin
  console, MCP, offline sync and export. These routes refuse the request. The
  viewer's own identity is never used in its place, and the request is never
  silently downgraded.
- **Never possible:** any write. That includes credentials: changing the
  person's password, email, passkeys or sessions, or anything else done
  in their name.
- **No side effects on the person:** no `last_active`, no read markers, no
  notification "seen", no recents or prefs writes, and no draft lookups.
  `getPage` skips the draft when the call is a view-as call.

Mechanism (mirrors the space view):

1. `POST /api/admin/users/{id}/view-as` with `{reason}` (1–500 characters, as for
   a space view). It checks the rules above, then stores
   `viewAs{id, session, viewer, target, tenant, until=now+1h}` in a bounded
   in-memory map. A session has at most one active view; a new one replaces it.
   The answer is `{id, until}`. The view is lost on a restart or failover, and
   the banner then says it ended. Audit: `view_as_started` (`data`, core,
   tenant-visible), with target, reason and until.
2. The web opens `/as/<id>` in a new tab. The app stores the id in
   `sessionStorage`, which is per tab, and the API client sends
   `PetalBook-View-As: <id>` on every call from that tab.
3. `handle` deals with a request that carries the header:
   - It refuses with `403 view_as_read_only` unless the route is marked
     **viewable**. Viewable is a new route-table flag that defaults to off.
     A source-scan test checks that every viewable route is a `GET`, and is not
     under `/api/admin`, `/api/users`, `/api/account`, `/api/notifications`,
     `/api/prefs`, `/api/connections`, `/api/sync`, `/mcp`.
   - It refuses a token or an OAuth token.
   - It refuses an unknown or expired id, or one opened by another session.
   - It checks the viewer still holds `tenant.users.viewAs` in the target's
     tenant: one `allow`.
   - It builds a principal: `User=target`, an **empty** `Access` (so no admin
     path such as `ViaAdmin` can open), `SessionID=""` (so no space view
     applies), and `ViewAs={viewer, id}`.
   - `openSpace` then filters by the space rule above and masks the
     permissions to read.
4. Audit rows have `actor=viewer`, `user=target`, `capacity` as in section 5,
   and `detail.viewAs=<id>`. Opening a page or file writes `page_viewed`
   (`data`, deduplicated per hour, as for space views).
5. `DELETE /api/admin/users/{id}/view-as` ends the view, and so do the exit
   button and the expiry. Audit: `view_as_ended`.

Key and feature: a new key `tenant.users.viewAs` (tenant scope, feature
`features.adminView`). It is grantable to custom roles, separately from
`tenant.data.view`. The built-in tenant and site administrators hold it.

`GET /api/session` with the header answers:

- the target's public profile: name, username and avatar. Their email is not
  sent, because the app does not need it;
- `permissions: []`;
- `viewAs: {id, viewer: {name}, until, hidden: n}`.

The app then renders as a reader, and its existing read-only rendering hides
every write control.

### 6.3 Web

- The person page's button works. It opens a small dialog with the reason (a
  bottom sheet on phones) and then opens the new tab.
- In the view tab there is a sticky banner above everything that cannot be
  dismissed: "Viewing as <name> · read only · 52 min left · Exit".
  - It respects `env(safe-area-inset-top)`.
  - On a phone it is one line, with an exit icon (40px target).
  - Exit ends the view and closes the tab, or goes to `/` when the tab cannot
    close.
- Hidden in the view: the notification bell, favourites, drafts, "new"
  buttons, the account menu (replaced by "Exit view") and the admin link.
- The view ending in another way (expiry, restart, losing the key) shows a
  full-page "This view has ended" with a button back to the console.
- The other tabs of the same browser are unaffected: the id is in this tab's
  `sessionStorage` only.

### 6.4 Cost

- Requests without the header pay nothing (one header lookup).
- A view-as request pays one map lookup, one `allow`, and the membership read
  that `openSpace` already does.
- `GET /api/spaces` in a view filters the person's list in memory. Its size is
  bounded by the switcher's own paging.
- Page-open audit is deduplicated per hour in the existing bounded table.

## 7. Dual-role scope selector: PROPOSAL, waiting for the owner

Status: **pending owner confirmation** (build order, "Person who is both site
admin and tenant admin"). It is its own PR, last in the order, and can be dropped
without touching sections 1–6.

The case: someone who holds site keys **and** administers one or more tenants.
That happens through a custom role or group grant today (`Subject.WithGrants`,
`internal/authz/subject.go:60`), or through 3.7 memberships later.
`SubjectFor` (`:141`) gives a site administrator only `Site`.

Proposed:

- **Permissions** are the union per scope, which sections 5's narrowing already
  gives: `Subject.Site ∪ Subject.Tenant[t]`, restricted to tenant keys in tenant
  scope. Site keys cover every tenant key, so holding both adds no power.
- **The selector** lists "Whole site", then **every tenant the person
  administers**, then "Other tenant…" for site keys. The first two come from
  `GET /api/session`: `adminScopes: [{kind:'site'}, {kind:'tenant', id, name}]`,
  built from the subject's non-empty tenant sets, which is cheap. The last
  scope used is remembered in `localStorage`, as a convenience.
- **Capacity**: in tenant scope, a key the person holds through `Subject.Tenant[t]`
  is recorded as `tenant_admin`, and otherwise as `site_admin`. A site
  administrator in a tenant they do not administer is therefore marked as a site
  action, and the tenant's administrators see it.
- Their personal and organisation membership is unaffected.

If dropped, section 5 still works: the selector shows "Whole site", the own
tenant and "Other tenant…", and the capacity of anyone holding site keys is
`site_admin`.

## 8. Security rules (all items)

- **View as a person** can never:
  - show a personal space's content;
  - show drafts, tokens, grants, sessions, connected accounts, emails, passkeys
    or notifications;
  - write anything;
  - change the person's credentials or account;
  - be used with a token or MCP;
  - outlive the opening session or one hour without a fresh, audited open;
  - reach a space outside the viewer's admin scope.

  It is bound to one session, it is reachable only through the viewable
  allowlist, and refusals never fall back to the viewer's identity.
- **Manage as tenant admin** can never:
  - use a site key in tenant scope (no personal spaces, no site admins' accounts,
    no plans or site rules, no purge, no site secrets);
  - read any secret's value (secrets stay write-only);
  - escape to another tenant: a mismatched header, `{tenant}` or `?tenant=`
    answers `404`.

  Every write records `capacity` and the tenant, and the tenant's
  administrators see it.
- **Organisations people create** never get a site administrator. The answers
  do not reveal whether an address has an account (`202` always). Caps are
  checked before any write. The slug is checked twice, and the transaction makes
  the tenant and the account together or neither.
- **Audit**: core categories cannot be turned off or trimmed below the 90-day
  floor. The CSV escapes cells that start with `= + - @` (formula injection).
  The download is audited.
