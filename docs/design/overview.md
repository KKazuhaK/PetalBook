# PetalBook design: overview

状态：草案，2026-11-21。第 0 期的验证已做完，正式实现尚未动工。仍标记为
「待验证」的条目没有在第 0 期解决，各自写明了留到什么时候。

PetalBook 是一个自托管的个人写作与笔记应用：内容是 Git 仓库里的 Markdown
文件，通过网页编辑，不需要懂 Markdown。它和 Rackbook 是姊妹项目，共用登录
协议层（authcore）和 Git 存储的做法，但是独立的仓库和独立的产品。

## 1. 目标与非目标

### 目标

- 三种内容用同一个模型：成系列的短文案、零散随记、长随笔，以及普通笔记。
- 完整的网页编辑体验：所见即所得，覆盖全部常用 Markdown 语法，支持图片和
  附件上传。
- 文件夹、标签、页面类型三种组织方式。
- 内容归用户所有：纯文本文件加 Git 历史，随时可以带走。
- 一两个人能零配置用起来，团队也能用：本地账号、OIDC、SAML、passkey。
- 每个人默认只看到自己的内容；可以建共享空间，按人或按组授权。
- AI 可以通过 MCP 读写。
- 最终能离线使用，并有桌面和手机客户端。

### 非目标

- 多人实时协同编辑（同一篇文档里看到别人的光标）。
- 单页级别的权限。权限只到空间。
- Markdown 表达不了的排版：文字颜色、分栏、任意嵌套的块。
- 多实例横向扩展。Git 工作目录在本地磁盘，服务是单实例。（第 5 期的主备冗余，5.17，
  是一台主机加一台备机，同一时间仍只有一个实例接请求。）
- 完整复刻 Notion 的数据库（公式、关联、汇总）。

### 应用的用法和官方构建（所有者 2026-11-23）

- **不登录的本地模式**：一个人、一台设备，不备份。内容就是本机的仓库，和单人形态
  （1.7）一样没有账号。
- **登录官方服务器，主要是为了协作**：几个人一起编辑、分享、多个空间、组织。同步和
  备份是随之而来的，不是登录的主要理由。
- **直接连自己的 Git 仓库**：不登录也可以在应用里连自己的仓库（GitHub、GitLab、任意
  Git 地址），同一个仓库可以在几台设备上用（见 4.7）。这是同步，不是实时协作。
- **应用商店里的官方构建只连官方服务器**（加上用户自己的仓库），**没有「服务器地址」
  这个设置**。想用自己的服务器的人改开源的客户端自己构建。所以 4.4 的「连接服务器」
  模式在官方构建里固定指向官方服务器。
- **开源的范围**：客户端和本地模式（包括连自己的仓库）开源。服务端以后可能不完全
  开源（像 RustDesk 那样的 open-core）；开发期间仓库保持公开（CI 免费）。
- **外部贡献要签 CLA**，这样官方构建才能一直上 App Store；两位维护者（Danika He、
  Kazuha Mo）也签，或者以后把权利归到一个主体。服务端和客户端用什么许可证未定，见
  第 13 节。

## 2. 核心决定

| 决定 | 选择 | 理由 |
|---|---|---|
| 事实来源 | Git 仓库里的 Markdown 文件 | 可移植、有历史、AI 友好，复用 Rackbook 的做法 |
| 权限单位 | 空间，一个空间一个 Git 仓库 | 私人内容物理隔离；团队功能以后加不用改模型 |
| 页面标识 | 文件头部的固定 ID，不依赖路径 | 改名、移动、离线同步、双向链接都靠它 |
| 编辑器 | Tiptap，存 Markdown | 生态最成熟；只开放 Markdown 能表达的功能以保证无损往返 |
| Markdown 转换 | 自己用 remark 写，不用 `@tiptap/markdown` | 实测 116 个用例，官方扩展过 75 个，自写转换层过 113 个，见 `spikes/markdown-roundtrip` |
| 标签与分类 | 写在每个文件的头部，查询走索引 | 跟着文件走，不产生集中文件的合并冲突 |
| 状态存储 | SQLite（默认）或 PostgreSQL | 用户、组、会话等不属于内容；不支持 MySQL 以控制测试成本 |
| 搜索索引 | 始终是本地 SQLite，逐字切分 | 可从文件重建的缓存；实测 5 万篇够用，不需要 Redis 或搜索服务 |
| 登录协议 | authcore 的 `oidc`、`passkey`、`saml` | 已有，Rackbook 在用 |
| 账号、会话、角色 | 本项目自己实现 | authcore 明确不包含账号模型 |
| Git 存储代码 | 先从 Rackbook 复制并解耦，第 3 期抽成独立模块 | 接口稳定前不发布，见第 10 节 |
| 草稿 | 存数据库，停笔后才合并成 commit | 自动保存不刷屏历史，丢盘不丢稿 |

## 10. 复用

| 来源 | 内容 | 方式 |
|---|---|---|
| authcore | `oidc`、`passkey`、`saml`，按需 `captcha` | 直接依赖 |
| Rackbook `internal/login` | 登录流程编排 | 复制后改成数据库账号 |
| Rackbook `internal/tokens`、`oauthserver`、`mcpauth` | API token、MCP 的 OAuth | 复制 |
| Rackbook `internal/gitstore`、`githubapp` | Git 读写 | 复制并解耦，见下 |
| Rackbook `web/` | 外壳、组件、i18n、rjsf 表单 | 复制 |

### Git 存储模块

1. 复制 `gitstore` 和 `githubapp`，去掉对 Rackbook `config`、`fsutil` 的依赖
   和写死的名字，整理成不依赖应用代码的包。
2. 在本项目里加多仓库、HTTPS 令牌、建仓库，把接口磨稳。
3. 第 3 期发布成独立模块，Rackbook 切过去。

期间负责安全保证的文件（主要是 `safegit.go`）尽量不动，有修复两边同时改。
进模块的是：受限的 git 执行器、凭据、fetch/提交/推送/重试、历史改写检测、
只读镜像。留在各自项目的是：Rackbook 的 `Store` 和 PR 模式，本项目的草稿、
合并、冲突副本和建仓库流程。这个模块不进 authcore。

### 引擎和服务端的边界（所有者 2026-11-23）

从现在起守住：**引擎包**（`space`、`gitstore`、`index`、`page`、`links`，以及 Markdown
的处理：Go 这边现在在 `links` 里用 goldmark，网页端是 `web/src/markdown`）**不依赖只有
服务端才有的包**（租户、登录和账号 `auth`、计费、多人权限 `perm` 之类）。这样以后可以
把客户端（本地模式、连自己的仓库，见第 1 节）单独拆出来。2026-11-23 查过一次：
`internal/space` 的依赖只有 `gitstore`、`page`、`links`、`index`、`langtag`，守着这条。
以后加一个测试（`go list -deps` 检查引擎包的依赖），让 CI 守着它；新代码要用服务端的
东西时，在服务端那一层包一下，不往引擎包里引。

## 12. 风险

| 风险 | 应对 |
|---|---|
| Markdown 往返不干净，文件每次保存都有无关差异 | 第 0 期先测；不行就换编辑器或自己写序列化 |
| 编辑体验工作量被低估 | 第 1 期范围里它排第一，其余可以后移 |
| 仓库被附件撑大 | 大小上限；存储接口留好对象存储 |
| 外部直接改文件把头部改坏 | fetch 后校验，标出问题页面，不丢内容 |
| 两份 Git 存储代码在抽模块前漂移 | 安全相关文件保持不动，修复同步 |
| 离线改动回来时盖掉别人的内容，或在设备上丢失 | 判断全在服务器，沿用 `baseRev` 和「从不隐式丢草稿」；合不了存成冲突副本；待同步的内容在设备上永不因空间上限被清（4.2） |
| 浏览器清掉离线数据（iOS 没安装的网站 7 天、存储满） | 安装到主屏幕、申请持久存储；未同步的改动在界面上一直可见，并能导出（4.2、4.5） |
| 旧的应用外壳按旧合同写入新服务器 | 重放之前核对接口版本，不对就先刷新（4.3） |
| 几万篇的空间让离线同步变慢 | 只取轻量目录和范围内的正文，之后按变更流只取改过的；轮询代价按改动数算（4.1） |
| 两个进程同时跑（滚动重启）时缓存和计数不一致 | 已知限制，写在各里程碑；5.3 经 PostgreSQL 共享 |

## 13. 已定与未决

- 项目名已定为 PetalBook，大写 B（配置目录仍是小写的 `.petalbook/`；只查过 GitHub 上的重名情况，Google、域名、商标未查）。
- 许可证：原先定为 AGPL-3.0（改了代码拿去提供服务的人必须公开改动；Rackbook 和
  authcore 是 Apache-2.0，与之兼容）。**所有者 2026-11-23 重新放开，未定**：客户端和本地
  模式开源，服务端以后可能是 open-core（第 1 节），所以服务端和客户端各用什么许可证要
  重新定；官方构建要上 App Store，许可证要和应用商店的条款相容（这也是要 CLA 的原因）。
- CLA 的文本、签署方式（例如 PR 上的机器人），以及两位维护者是各自签还是把权利归到
  一个主体：未定（所有者 2026-11-23 定了「要 CLA」）。
- 文档语言：本文是中文；公开仓库的 README 和设计文档是否以英文为主。
