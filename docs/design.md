# PetalBook 设计与分期计划

状态：草案，2026-11-21。第 0 期的验证已做完，正式实现尚未动工。仍标记为
「待验证」的条目没有在第 0 期解决，各自写明了留到什么时候。

PetalBook 是一个自托管的个人写作与笔记应用：内容是 Git 仓库里的 Markdown
文件，通过网页编辑，不需要懂 Markdown。它和 Rackbook 是姊妹项目，共用登录
协议层（authcore）和 Git 存储的做法，但是独立的仓库和独立的产品。

## 1. 目标与非目标

### 目标

- 三种内容用同一个模型：成系列的短文案、零散随记、长随笔，以及普通笔记。
- 完整的网页编辑体验：所见即所得，覆盖全部常用 Markdown 语法，支持图片和
  附件上传。
- 文件夹、标签、页面类型三种组织方式。
- 内容归用户所有：纯文本文件加 Git 历史，随时可以带走。
- 一两个人能零配置用起来，团队也能用：本地账号、OIDC、SAML、passkey。
- 每个人默认只看到自己的内容；可以建共享空间，按人或按组授权。
- AI 可以通过 MCP 读写。
- 最终能离线使用，并有桌面和手机客户端。

### 非目标

- 多人实时协同编辑（同一篇文档里看到别人的光标）。
- 单页级别的权限。权限只到空间。
- Markdown 表达不了的排版：文字颜色、分栏、任意嵌套的块。
- 多实例横向扩展。Git 工作目录在本地磁盘，服务是单实例。
- 完整复刻 Notion 的数据库（公式、关联、汇总）。

## 2. 核心决定

| 决定 | 选择 | 理由 |
|---|---|---|
| 事实来源 | Git 仓库里的 Markdown 文件 | 可移植、有历史、AI 友好，复用 Rackbook 的做法 |
| 权限单位 | 空间，一个空间一个 Git 仓库 | 私人内容物理隔离；团队功能以后加不用改模型 |
| 页面标识 | 文件头部的固定 ID，不依赖路径 | 改名、移动、离线同步、双向链接都靠它 |
| 编辑器 | Tiptap，存 Markdown | 生态最成熟；只开放 Markdown 能表达的功能以保证无损往返 |
| Markdown 转换 | 自己用 remark 写，不用 `@tiptap/markdown` | 实测 116 个用例，官方扩展过 75 个，自写转换层过 113 个，见 `spikes/markdown-roundtrip` |
| 标签与分类 | 写在每个文件的头部，查询走索引 | 跟着文件走，不产生集中文件的合并冲突 |
| 状态存储 | SQLite（默认）或 PostgreSQL | 用户、组、会话等不属于内容；不支持 MySQL 以控制测试成本 |
| 搜索索引 | 始终是本地 SQLite，逐字切分 | 可从文件重建的缓存；实测 5 万篇够用，不需要 Redis 或搜索服务 |
| 登录协议 | authcore 的 `oidc`、`passkey`、`saml` | 已有，Rackbook 在用 |
| 账号、会话、角色 | 本项目自己实现 | authcore 明确不包含账号模型 |
| Git 存储代码 | 先从 Rackbook 复制并解耦，第 3 期抽成独立模块 | 接口稳定前不发布，见第 10 节 |
| 草稿 | 存数据库，停笔后才合并成 commit | 自动保存不刷屏历史，丢盘不丢稿 |

## 3. 数据模型

### 3.1 空间的目录结构

```
<space>/
  .petalbook/
    space.yml            # 空间配置：文件夹绑定的页面类型、默认视图
    types/
      文案.json          # 页面类型：额外属性的 JSON Schema
  Tang/
    暮雪.md
    残阳.md
  随笔/
    2026/
      某篇长文.md
  收件箱/
    2026-11-21-k3f9.md
  assets/
    01JD…/               # 按页面 ID 分目录
      photo.jpg
```

### 3.2 页面文件

```markdown
---
id: 01JD3K8Q7Z
title: 暮雪
subtitle: 下一个路口吧 等水洼把天空还回来
source: 《某本书》第三章
tags: [玉兰, 栀子, 黄昏]
created: 2025-12-03
series: 冬季
status: 定稿
---
你听得见今天屋檐滴水的声音么？……
```

- **内置字段**：`id`、`title`、`subtitle`、`source`、`tags`、`created`。除 `id`
  外都可以为空。零散随记可以没有标题。`source` 是来源（出处）：一个人、一本
  书、一个网址，自由填写，参与搜索。
- **类型字段**：`series`、`status` 这类由页面类型的 schema 定义。
- **正文**：GFM Markdown。
- **更新时间**不写进文件，由索引从 Git 提交时间得出。
- **文件名**取自标题，去掉文件系统不允许的字符；没有标题时用日期加短 ID；
  重名加后缀。改标题会重命名文件，`id` 不变。
- **`《标题》｜副标题`** 只是文案类型的显示模板，不写进文字。

#### 没有标题的页面

只有一句话或一小段的文案不需要标题，这是正常情况，不是残缺的页面：

- 头部没有 `title` 字段（不是空字符串），文件名用日期加短 ID，例如
  `2026-11-21-k3f9.md`。
- 在列表、搜索结果、链接和浏览器标签里，用正文的第一行（截到约 30 字）
  代替标题显示，并用较浅的颜色区别于真正的标题。
- 卡片视图和连读视图里直接显示正文，不留标题的位置，也不显示
  `《》｜` 模板。
- 编辑时标题栏是一行浅色的占位，不填就不存在；光标默认落在正文。快速
  记录创建的就是这种页面。
- 以后补上标题时，文件改名为标题，`id` 不变，指向它的链接不受影响。
- 按标题排序时，没有标题的排在最后，彼此按创建时间排。
- 「同一文件夹内标题重复」的校验不看没有标题的页面。

### 3.3 组织方式

- **文件夹**：就是目录，可无限嵌套。一篇只在一个位置。
- **标签**：一篇多个，跨文件夹。允许 `花/栀子` 这种层级写法。写在每篇的
  头部；标签自身的属性（颜色、说明、排序）放在 `.petalbook/tags.yml`。
  重命名标签会在一次提交里改所有用到它的文件。
- **页面类型**：一个文件夹可以在 `space.yml` 里绑定类型，其下页面继承。
  类型决定属性面板里有哪些字段（由 JSON Schema 生成表单，复用 Rackbook 的
  rjsf 用法），以及文件夹有哪些视图。
- **排序**：按名称、创建时间、更新时间。手动拖动排序第一版不做。

### 3.4 附件

- 上传到 `assets/<页面 ID>/`，正文里用相对路径引用。
- 默认单文件上限 10 MB，可配置。
- 存储走接口，每个空间选一种后端：
  1. **空间仓库内**（默认）：`assets/` 目录，最简单。
  2. **独立的附件仓库**：另一个 Git 仓库，文字仓库保持小而快。用和空间
     相同的凭据方式。页面提交前先确保它引用的附件已推送。
  3. **S3 兼容存储**（之后）。
- 无论哪种后端，私有内容的附件都由本服务读出并经过权限检查后返回，不直接
  给出仓库或 CDN 的公开链接。公开链接只用于已发布的页面（第 14 节）。
- 上传前在浏览器里可选压缩和转 WebP，文件名加内容哈希去重。
- 页面删除或引用移除后，孤立附件由清理任务处理，不立即删。

### 3.5 校验

沿用 Rackbook `check` 的思路，对每个空间检查：

- `id` 缺失、重复、格式错误。
- 头部不是合法 YAML，或类型字段不符合 schema。
- 指向不存在页面的链接、指向不存在文件的附件引用。
- 同一文件夹内标题重复（提示，不阻止）。

有问题的页面在界面上标出来让人修，不拒绝加载整个空间。

## 4. 存储与同步

### 4.1 两种模式（每个空间单独选）

1. **仅本地**：仓库只在服务器上。
2. **远端为准**：照搬 Rackbook。服务器持有一份克隆，定时 fetch 并快进；
   每次写入是 fetch、重置到远端、提交、推送，被拒就重来。从不 force push。
   检测到远端历史被改写就转只读，等管理员确认。本地克隆丢了可以重新拉。

可选的第二个远端只作为「只推不拉」的镜像，不参与冲突判断。

### 4.2 创建空间

- 服务器自己 `git init` 并写入 `.petalbook/space.yml`，不需要模板仓库。
- 选了远端时，按凭据类型自动建仓库或使用用户给的地址。

### 4.3 远端凭据（每个空间单独选）

| 方式 | 适用 | 来源 |
|---|---|---|
| SSH 部署密钥 | 任何 Git 服务 | Rackbook 已有 |
| GitHub App | 组织下自动建仓库 | Rackbook 已有，需扩展建仓库；权限见下 |
| HTTPS 访问令牌 | GitHub、Gitea、GitLab | 新写，沿用 GitHub App 传令牌的方式 |
| GitHub 用户授权 | 个人账号下建仓库 | 新写 |

建仓库所需的权限（2026-11-21 查 GitHub 官方文档）：

- 组织下建仓库是 `POST /orgs/{org}/repos`，个人账号下是 `POST /user/repos`。
  权限对照表把两者都列在 Administration 的 write 级别下，并标注安装令牌和
  用户令牌都可用。
- 用户令牌通过网页授权或设备码流程获得，默认 8 小时过期，刷新令牌 6 个月
  过期，所以要存刷新令牌并自动续期。用户令牌的权限是「用户有的」和「App
  有的」的交集。
- 文档没有说明的两点，要在第 2 期用一个测试 App 实际试：这个 Administration
  是组织级还是仓库级权限；App 建出的新仓库，在安装范围是「仅选定仓库」时
  是否自动可访问。

凭据存数据库，用服务器密钥加密。令牌只通过环境变量传给 `git`，不出现在
命令行、远端地址、`.git/config` 或日志里。

### 4.4 草稿与提交

- 编辑时内容持续保存为草稿（数据库，按页面和用户）。草稿记录它基于的版本。
- 合并成 commit 的时机：停笔 2 分钟、离开页面、用户点「保存版本」，或距上次
  提交超过 10 分钟。
- commit 的作者是编辑者，提交者是服务。

### 4.5 本地空间不够时：部分缓存

占空间的主要是附件和 Git 历史，不是文字：5 万篇、6220 万字的文字只有
192 MB，索引 166 MB。所以文字和索引始终完整留在本地，其余的可以按需取：

- **附件**：用独立附件仓库或 S3 后端时，本地只留一个有大小上限的缓存，
  最近用过的留着，其余的在打开页面时再取。附件仓库用 Git 的部分克隆
  （不预先下载文件内容）实现。
- **Git 历史**：空间仓库可以只保留最近的历史，更早的版本在查看历史时再向
  远端取。
- **以后的离线客户端**：可以选同步哪些空间；文字全量同步，附件按需下载并
  有缓存上限。

限制：仅本地的空间没有别的副本，不能做部分缓存；远端连不上时，没缓存到
的附件和旧版本看不了，界面上要明确提示。部分克隆需要放宽受限 git 执行器
允许的命令，这点待验证（做附件缓存时验证，不在第 0 期范围内）。

所有者 2026-11-22 明确：用户多了以后本地一定放不下，**不能要求每个空间都
在本地有完整克隆**。按收益从大到小，分四步（都只对跟随远端的空间成立，
因为远端才是那份真的；只在本地的空间是唯一的一份，只能靠配额或把附件放到
对象存储）：

1. **闲置的空间整个从本地删掉**，下次打开时再取回。现在闲置只是关闭，
   克隆还留着。跟随远端的空间每次改动都已推送，本地没有独有的东西，删掉
   是安全的；索引可以留着（它很小），这样列表和搜索不用等取回。
2. **只取最近的历史**（浅克隆），看历史时再按需向远端要更早的提交。
3. **不取大文件的内容**（Git 的部分克隆，`--filter=blob:none` 或按大小），
   附件在有人打开页面时才取，本地只留一个有上限的缓存。
4. **连正文也按需取**：本地只有索引和最近打开的页面。

第 3、4 步要远端支持部分克隆（GitHub、GitLab 支持），也要放宽受限 git
执行器允许的命令，都还没验证过；做之前先单独验证一次。打开一个被删掉的
空间要等一次网络往返，远端连不上时这个空间就打不开，界面要说清楚。

### 4.6 外部改动与冲突

- fetch 到新提交后重建受影响页面的索引并跑校验。
- 草稿提交时如果基于的版本已不是最新：先做三方文本合并；合不了就把草稿
  存成一篇新的「冲突副本」，两边都不丢。
- 同一套规则用于：GitHub 上直接改、另一个浏览器标签页、将来的离线客户端。

## 5. 数据库

### 5.1 状态库（SQLite 或 PostgreSQL）

用户、外部身份（提供方加 subject）、密码和 passkey、组和成员、空间和成员、
会话、API token、OAuth 授权、远端凭据（加密）、草稿、邀请。

- SQLite 用纯 Go 驱动，保持单个可执行文件。
- 两种数据库从第一期起都在 CI 里跑测试，避免事后补兼容。
- 接 PostgreSQL 的收益是托管备份和现成运维，不是横向扩展。

### 5.2 索引库（始终本地 SQLite）

页面元数据、全文索引、标签、链接关系。可以随时删掉，从文件重建。

- 中文全文搜索用「逐字切分」：入库前在每个汉字两边加空格，让 SQLite 自带
  的分词器把每个字当成一个词，查询时转成短语。三字符分词查不了两个字的
  词，已排除。
- 全局搜索跨当前用户可见的所有空间，结果按空间权限过滤。
- 列表、文件夹树、标签、搜索都查索引，不遍历磁盘，不逐个读文件。
- 索引记录它对应的提交。每次 fetch 快进后，比较新旧两个提交之间改了哪些
  文件，只重建这些页面的索引：新增的加入，删除的移除，改名的靠 `id` 认出是
  同一篇。别人直接在 GitHub 上改动就是走这条路径，最多延迟一个 fetch 周期
  （默认 60 秒）；配置了 webhook 时可以立即触发。
- 只有索引缺失、版本不符，或记录的提交已不在历史里时才全量重建。
- 不引入 Redis：服务是单实例，会话在状态库，热数据放进程内缓存即可。
- 实测（5 万篇、6220 万字，见 `spikes/search-scale/`）：文件夹和标签列表
  0.1 到 15 ms；搜索少见的词 0.2 ms，搜索命中上万篇的常见词约 200 ms；
  保存一篇后更新索引 0.7 ms；全量重建 29 秒；索引大小是文本的 87%。
- 已知要改进的：逐字切分会跨标点匹配，入库时要把标点换成占位词。

## 6. 登录与权限

### 6.1 登录方式

| 方式 | 说明 | 期 |
|---|---|---|
| 本地账号 | 密码，首次启动创建管理员，邀请链接加人，默认不开放注册 | 1 |
| OIDC | authcore `oidc`，沿用 Rackbook 的配置形状 | 1 |
| passkey | authcore `passkey`，本地账号和外部账号都能绑定 | 2 |
| SAML | authcore `saml` | 2 |

管理员可以配置启用哪些方式。

### 6.2 角色

- **实例级**：管理员、成员。
- **空间级**：所有者、可编辑、只读。
- **私人空间**：每个用户自动创建一个，只有本人是成员。
- **管理员能看全部**（所有者 2026-11-22 的决定，取代原先「管理员在界面和
  API 里看不到别人的私人空间」）：管理员可以查看和管理服务器上所有空间和其中
  的内容。原因是它本来就挡不住能访问服务器磁盘的人，做成看不见只是假象。
  真正对管理员保密要靠下面的加密空间。在 1.7 实现之前，接口仍是旧行为。
- **预留：加密空间**。内容在浏览器里加解密，服务器和仓库里只有密文，管理员
  物理上看不到。代价要写明：服务端搜索、历史对比、服务端渲染、找回密码都
  做不了或要另想办法。现在不做，只守住两条：权限检查不假定服务器读得到
  正文；页面的读写接口将来可以换一种「正文是密文」的形态。
- **预留：自定义角色**。内置的所有者、可编辑、只读之外，以后可以自己定义
  角色，由一组权限组成（看、编辑、删除、管理成员、管理同步和导入等）。所以
  权限检查从一开始就按「这个人对这个空间有没有某项权限」来写，角色只是
  权限的集合，不在代码里到处比较角色名。
- **共享空间**：成员可以是用户或组。
- **组**：来自 OIDC/SAML 的组声明（做映射），或在应用里手动建。

### 6.3 机器访问

- API token：限定到空间，分只读和读写。
- MCP 在 `/mcp`，沿用 Rackbook 的实现，两种接入方式都支持：
  1. **直接连接**：本服务自带 OAuth 授权服务，任何支持 MCP 的客户端填地址
     就能连；也可以用 API token。
  2. **经 MCPHub**：接受 MCPHub 签发的令牌，每个人用自己的身份调用。
     MCPHub 的用户在本应用里作为一种外部身份绑定到账号上。
- MCP 的权限和网页完全一致：只能看到自己有权访问的空间，只读成员不能写。
- 工具：列出空间和文件夹、搜索、读取页面、新建、修改、移动、打标签、
  查看历史。搜索和列表走同一个索引。写入同样走草稿与提交规则，提交的
  作者是令牌对应的人，并在提交信息里注明来自 MCP。

## 7. 编辑器

- 所见即所得，`/` 命令菜单、选中文字弹出格式工具栏、拖动手柄调整块顺序。
- 支持：标题、粗体、斜体、删除线、行内代码、链接、无序/有序/待办列表、
  引用、代码块（带语言高亮）、表格、图片、附件、分割线、脚注。
- 图片：粘贴、拖入、点击上传；可填说明文字。
- 熟悉 Markdown 的人可以直接打 `#`、`-`、`>` 等快捷输入。
- **链接**：光标在链接里时弹出小浮层，可以改地址、改文字、打开、去掉链接。
- **表格**：加行、加列、删行、删列、删表、设置列对齐，从单元格旁的菜单
  操作。Markdown 表格必须有且只有第一行是表头，所以表头行不能关掉；删掉
  表头行后下一行自动成为表头。不支持合并单元格。

### 7.0 三种编辑模式

每篇文档右上角可以切换，默认是所见即所得，选择按用户记住：

1. **所见即所得**：默认，不需要懂 Markdown。
2. **Markdown 原文**：直接编辑整个文件的文本，包括头部字段。这是保底手段：
   编辑器处理不了或显示不对的内容，总能在这里改。用带 Markdown 高亮的
   代码编辑器（CodeMirror）。
3. **左右对照**：左边原文，右边所见即所得，两边都能改，互相同步，滚动联动。

规则：

- 在原文里打的字原样保留，保存的就是你写的文本。
- 一旦从所见即所得一侧改动，正文会被重写成统一写法：内容不变，但比如
  `*` 列表会变成 `-`，表格的分隔行会被规整。这是一次性的，之后稳定。
- 原文里头部写坏了（不是合法 YAML、`id` 被删）时不能切回所见即所得，
  界面指出是哪一行，改好再切。
- 大文档在左右对照模式下，同步要做防抖（5 万字的文档一次转换约半秒）。
- 不提供 Markdown 表达不了的功能，保证文件无损往返。
- 第 2 期：`[[链接]]` 到其他页面，按 ID 存，显示标题。

### 7.1 往返验证的结论（2026-11-21）

验证代码和完整结果在 `spikes/markdown-roundtrip/`。

- 编辑器用 Tiptap，但 Markdown 的读写不用官方扩展，自己基于 remark 实现
  「编辑器文档 ↔ mdast ↔ Markdown 文本」。
- 116 个用例里，官方扩展只过 75 个：中文标点旁的粗体会丢，行首的 `#`、`-`
  不转义，含空格的图片地址写坏。自写转换层过 113 个。剩下 3 个里，2 个是
  粗体边缘的空格被移到粗体外面，肉眼看不出；1 个是正文里的裸网址重新打开
  后变成链接，这是看得见的变化，要改成把裸网址写成 `<网址>`。
- 转换层只处理正文。文件头部要先切下来单独解析，这部分还没写。
- 编辑器里没有对应形式的写法在读入时改写一次：引用式链接变成行内链接，
  有序列表里的待办变成无序的。
- 中文标点旁的强调用 `remark-cjk-friendly`。这不是标准 CommonMark：在
  GitHub 网页上直接看原文件会显示出星号。本项目所有渲染 Markdown 的地方
  （编辑器、服务端、公开发布）必须用同一套规则。
- 看不懂的内容不丢：原始 HTML 作为不可编辑的块原样保留；脚注有专门节点。
- 保存时丢掉看不见也存不下的东西：段落、标题、单元格末尾的空格和换行，
  单元格开头的空格，文档结尾的空段落。全角空格保留。
- 约定的写法：硬换行用行尾反斜杠，空段落写成单独一行的 `<br>`，表格不做
  列对齐填充，单个 `~` 不算删除线，不提供下划线。
- 性能：5 千字读入 74 ms、存出 20 ms；5 万字读入约 0.5 秒。自动保存要防抖。

### 7.2 浏览器实测的结论（2026-11-21）

用真实键盘事件和粘贴在浏览器里测过（`spikes/markdown-roundtrip/browser/`），
输入快捷写法、快捷键、富文本粘贴都正常，每一步「存出再读回」都一致。
正式实现要补三件事：

- 自己写强调的输入规则。Tiptap 自带的要求 `**` 前面是空格或行首，紧跟汉字
  时不触发。
- 自定义纯文本粘贴：单个换行变成段内换行，空行才分段。默认行为把每一行
  都变成段落，诗行和分行文案会被打散。
- 粘贴 Markdown 源码时用转换层解析成排版后的内容。

### 7.3 服务端渲染（2026-11-21）

服务端用 goldmark 加 `goldmark-cjk-friendly` 扩展渲染 Markdown。拿编辑器
实际写出的 116 份 Markdown 对比前端和 Go 的渲染结果，114 份一致；不加扩展
是 106 份，不一致的主要是中文标点旁的强调。详见 `spikes/render-parity/`。

剩下 2 份要在转换层里改：粗体和斜体部分交叠时改用 `_` 表示斜体，避免连续
四个星号的歧义；正文里的裸网址统一写成 `<网址>`。这份对比测试要进 CI。

还没验证的：真实文案的全量往返（测试里用的是编写的示例，等内容导入之后）；
数学公式。
中文输入法的组合输入也还没验证：自动化测试不经过输入法，需要真人用拼音
输入法在测试页的列表、表格、行内代码里试。

## 8. 前端

### 8.1 技术

React、Vite、Tailwind、shadcn 组件、TanStack Query、react-router、cmdk，
与 Rackbook 一致，外壳和 i18n 机制复制过来。不用 refine（它服务于表格式
后台，这里用不上）。界面从第一期起支持中文和英文。

### 8.2 布局

- **左栏**：空间切换、快速记录、搜索（⌘K）、收件箱/最近/收藏、文件夹树、
  标签。可收起。
- **中间**：文件夹视图或编辑器。
- **右栏**（按需展开）：属性、目录、反向链接、版本历史。

### 8.3 页面编辑

- 顶部是标题，下面一行副标题（空时显示浅色占位，文案类型默认展示），
  再下面是标签和类型属性，然后是正文。
- 正文限宽，按中文阅读调行高和字距；提供无衬线和衬线两种正文字体。
- 右上角显示保存状态：「草稿已保存」「已提交」「离线」。
- 专注模式：隐藏两侧栏，只留文字。

### 8.4 文件夹视图

- **列表**：标题、副标题、标签、更新时间。
- **卡片**：适合短文案，直接显示 `《标题》｜副标题` 和正文，一屏读很多条，
  效果接近现在 Notion 那一页。
- **表格**：绑定了类型的文件夹可用，列是类型属性，可筛选排序，单元格内
  直接改枚举和日期（沿用 Rackbook 的做法）。
- **连读**（第 2 期）：把一个文件夹或一个系列按顺序排成一篇长文，像翻一本
  集子。
- **看板**（第 2 期）：按某个枚举属性分列，比如状态或系列，拖动改值。
- **时间线/日历**（之后）：按创建日期排布，适合日记和随记。
- **画廊**（之后）：以页面里第一张图作封面。

视图只是「筛选、排序、分组、展示方式」的组合，同一批页面可以存多个视图，
配置写在 `space.yml` 里。标签页和搜索结果也能用这些展示方式。

### 8.5 快速记录

任何页面按快捷键或点按钮弹出一个小输入框，写完进收件箱，之后再归类。
手机上是常驻的浮动按钮。

### 8.6 手机

单栏。左栏变成抽屉，底部是导航和快速记录；编辑时格式工具栏贴在键盘上方。
第一期就做成可安装的 PWA（只是可安装，离线在第 4 期）。

### 8.7 历史与差异高亮

目标是 Google Docs 版本记录那样的体验：不懂 Markdown 的人一眼看出改了什么。

- **版本列表**在右栏，按天分组，显示时间和编辑者。一个版本就是一次提交。
  可以给版本起名字（比如「初稿」「投稿版」），起了名字的版本置顶显示。
- **差异直接标在排版后的正文上**：新增的字绿色底，删除的字红色加删除线，
  留在原位。不是左右两栏的代码式对比。
- **按字比较**。先按块（段落、标题、列表项）对齐，没变的块原样显示；变了
  的块在内部按词和字比较。中文分词用浏览器自带的 `Intl.Segmenter`。
- **格式变化也标出来**：只是加粗、改标题级别这类没有文字变化的修改，用
  另一种颜色的下划线提示。
- **头部字段的变化**（标题、副标题、标签、状态）在正文上方单独列出。
- **图片和表格**：图片被替换时并排显示新旧两张；表格按单元格标色。
- 默认和上一个版本比，也可以任选两个版本比。可以切换到原始 Markdown 的
  逐行对比，给习惯看文本的人。
- **恢复**到某一版是产生一个新提交，不改写历史。
- 共享空间里按编辑者用不同颜色（第 3 期）。

实现上，把两个版本的 Markdown 各自转成编辑器文档，在文档树上做比较，结果
用只读编辑器加高亮装饰渲染。比较在浏览器里按需计算，只在打开历史面板并
选中版本时发生；服务端只负责给出版本列表和某一版的文件内容。

## 9. API 形状

REST，前端只通过它与后端交互，将来的客户端复用。

- `GET /api/spaces`，`POST /api/spaces`
- `GET /api/spaces/{s}/tree`：文件夹树
- `GET /api/spaces/{s}/pages?folder=&tag=&type=&q=`
- `GET /api/spaces/{s}/pages/{id}`：返回内容和当前版本
- `PUT /api/spaces/{s}/pages/{id}/draft`：带 `baseRev`
- `POST /api/spaces/{s}/pages/{id}/commit`
- `GET /api/spaces/{s}/pages/{id}/history`
- `POST /api/spaces/{s}/assets`
- `GET /api/spaces/{s}/changes?since={rev}`：某版本之后改了什么（同步用）
- `GET /api/search?q=`：跨当前用户可见的所有空间

`baseRev` 和 `changes` 从第一期就按离线同步的需要设计，即使当时只有在线
网页在用。

#### 里程碑 1.1 的现状（2026-11-21）

已完成并通过提交前审查。实现上和上文不同或新增的地方：

- **本地草稿**：编辑内容在改动后约 0.7 秒写入浏览器本地存储，页面隐藏、
  刷新、关闭时再同步写一次；只有服务器确认存下同样内容后才清除。下次打开
  时自动恢复，或在服务器版本已变时进入冲突对话框。30 天过期。它防的是还没
  发到服务器的内容丢失，只在当前浏览器有效；跨设备的保护靠 1.2 的服务端
  草稿。
- **后台提交只包含服务器自己写过的文件**，待提交的路径记在状态目录的日志
  里，崩溃后重启会接着提交。仓库处于合并、变基等操作中时暂缓提交。手动放
  进空间的文件不会被自动提交。
- **跨站请求**一律拒绝，规则见 `docs/api.md`。开发时要用 `--allow-origin`
  列出网页的地址。
- **不监视磁盘**：服务器之外的改动在重启或重建索引后出现在列表里；按 ID
  访问单篇时总会核对文件。
- `make contract` 把前端的接口测试对着真实服务器跑一遍，防止前端的模拟
  服务器和真实行为不一致。

审查留下、不阻塞的已知问题，带到 1.2：

- 提交日志有三个窄窗口：保存与提交快照交错时可能漏记一条；崩溃打断追加后
  下一条记录可能失效（需要连续两次崩溃）；服务器建的文件在恢复前被外部改过
  时不会被自动提交。三种情况文件内容都完好，只是暂时不在 Git 历史里。
- 仓库长时间处于变基中时，提交日志会一直增长。
- 标签列表里的非文字项（如空值）在界面上删不掉。
- 没有头部或头部损坏的 `.md` 文件只记在启动日志里，界面上看不到。
- 对外监听（`--insecure-no-auth`）在有登录之前不安全，见 `docs/api.md`。

#### 里程碑 1.2 的现状（2026-11-21）

接口见 `docs/api.md`。实现上定下来的、上文没有写或写得不同的地方：

- **两种启动方式**：`--space 目录` 是单人免登录（即 1.1）；`--data 目录` 是
  账号模式，空间在 `目录/spaces/<空间 ID>/`，索引在 `目录/cache/`，状态库
  默认是 `目录/petalbook.db`，用 `PETALBOOK_DATABASE` 换成 PostgreSQL。单人
  模式也有状态库（放草稿），和账号模式走同一套代码。
- **第一个管理员**：没有任何账号时，启动日志里打印一次性的设置链接；可以设
  密码，也可以直接用 OIDC 登录来创建。没人能登录时用 `petalbook user
  add|passwd` 直接改数据目录。
- **加人**靠邀请链接（默认 7 天，用一次）。OIDC 首次登录自动建号要加
  `--oidc-auto-create`。账号只按签发方加 `sub` 匹配，不看邮箱。
- **空间**：每个账号自动有一个个人空间，可以再建，默认每人最多 20 个
  （`--max-spaces`）。空间按需打开，闲置 15 分钟或同时打开超过 64 个时关闭
  最久没用的。提交的作者是空间所有者，提交者是服务。
- **草稿**（改了 4.4 的细节）：每份草稿有一个版本号，存草稿、提交、删除都要
  带上自己上次看到的版本，对不上就拒绝，由界面弹出冲突对话框；同一个人在两台
  设备上写同一页不会互相覆盖。**服务器从不隐式丢弃草稿**：直接保存页面文件
  时草稿留着（变成过期，下次打开让人选），只有提交、点名版本的替换或删除、
  删除页面本身才会让一份草稿消失。客户端因此不必猜“服务器上的是不是我的”：
  没有未保存内容时，服务器上变了就直接显示服务器的；切回标签页时会主动看
  一眼，在别的设备上改过的内容会直接出现。停笔 2 分钟或草稿存在满 10 分钟，服务器自己
  写入文件；写入后几秒内提交到 Git（`--commit-idle` 的默认值因此从 2 分钟
  改成 5 秒）。页面文件不在了的草稿不删除，用 `petalbook draft list|export`
  取回。
- **本地草稿**按用户、空间、页面三者存，换账号登录不会看到别人的。服务器确认
  存下草稿后，本地副本标记为“已确认”，此后不参与任何判断（不会隔天把旧文字
  当冲突弹出来），只在页面被别处删除时用来找回文字；文字进了文件就清掉。
- **草稿状态机的验证**：客户端所有“服务器和我以为的不一样”的情况走同一张
  规则表（`web/src/editor/reconcile.ts`）。`model.*.test.ts`（共用 `modelHarness.ts`）用随机序列驱动真实
  的控制器和恢复逻辑，对着和真实服务器规则一致的模拟服务器跑（约九千种顺序，
  含丢回应、服务器自动写入、第二台设备、离线、刷新），每步检查八条不变量。
- **状态库**：SQLite 和 PostgreSQL 用同一份表结构和同一套测试
  （`make test-postgres` 起一个临时的 PostgreSQL 来跑；CI 两种都跑）。
  会话只存令牌的哈希，查询走进程内缓存。

已知问题，带到后面：

- 有人持续对某个用户名输错密码，可以让这个用户名一直无法用密码登录（每次
  最多锁 5 分钟，但可以接着锁）。要彻底解决得区分可信的来源地址。
- 命令行对账号的改动（改密码、加人）最多 5 分钟后才被运行中的服务看到。
- 账号模式下改空间名只改数据库，不改 `space.yml`。
- OIDC 没有对着真实的身份提供方跑过，只有用假提供方的自动化测试。
- 头部里超过 2^53 的整数，编辑任何字段后会被改写成丢了精度的值（1.1 就有）。
- 文件在应用之外被改、而编辑器内容等于它上次知道的文件时，要到下一次请求
  才发现。
- 两个标签页开同一页的行为只有单元测试，没有在真实浏览器里测过。
- 页面头部超过 16 KB 时，历史读不到这页的版本（判断一个版本属于哪一页只读
  文件开头这么多）。
- 模型测试看不出“服务器隐式丢草稿”这条规则被破坏（它的第二台设备会不看
  就替换草稿，所以相应的不变量放宽了）；这条规则靠单元测试和接口测试守住。
- 命令行和单人模式的测试只在 SQLite 上跑；账号模式的测试两种数据库都跑。
- 服务是单实例的：两个进程共用一个 PostgreSQL 时，草稿的自动写入和空间
  数量上限没有跨进程的保护。
- 1.1 留下的提交日志窗口、头部损坏的文件在界面上看不到，仍未处理。

#### 里程碑 1.3 的现状（后端，2026-11-21）

接口见 `docs/api.md`。实现上定下来的、上文没有写或写得不同的地方：

- **Git 层**是 `internal/gitstore`，不依赖应用其他部分：受限执行器（每条 git
  命令都先过 `safegit.go` 的白名单，推送永远是 `push --quiet origin
  HEAD:refs/heads/<分支>`）、令牌和 SSH 密钥、取回/快进/只提交指定路径/推送/
  撤销、改写检测、页面历史。本地空间的提交也走它，进程里只有一处启动 git。
  白名单相对 Rackbook 多出的项目都在 `safegit.go` 里逐条写了理由。
- **传输**只有 https 和 ssh（`GIT_ALLOW_PROTOCOL`，地址校验也拒绝其他形式）。
  令牌经环境变量交给固定的凭据助手；SSH 私钥只在一条命令的时间里以 0600 文件
  存在于 0700 临时目录；主机密钥首次连接时信任，之后变了就是 `error` 状态。
  每条网络命令有超时，到点杀掉整个进程组。
- **远端空间的写入**在空间锁里做完整一轮：取回（几秒内取过则跳过）、快进、
  应用、只提交这次改的路径、推送；被拒就撤销（一个 `reset`、一个 `ls-tree`、
  一个 `checkout`）再在新状态上重来，最多 4 次；回应丢了的推送先查远端是否已
  收下。读不等网络：读不拿空间锁。草稿提交时不握着草稿锁等网络，所以远端慢
  或断开时输入照常保存。
- **崩溃恢复**不碰网络：打开空间时把日志里记着的未提交文件提交掉；之后第一次
  同步（每次打开都会立刻排一次）推送它们，远端已前进则把没推送的提交留在
  `refs/petalbook/unpushed/<时间>`，克隆移到远端，状态记为 `error`，说明里写
  着这个引用。工作区里有不是服务器改的内容时拒绝写入（`error`，不动那些改动）。
- **拉取放在管理器里**：一个循环，只看当前打开的、跟着远端的空间，按
  `--pull-interval` 加抖动轮流取，同时最多 4 个。关闭的空间不拉（没人在看），
  下次打开时立刻拉一次。拉取不算“使用”，所以只被拉取的空间照样会因闲置而关闭。
- **索引**在快进后只更新两个提交之间改动的文件（`index.Refresh`），超过 2000
  个文件才退回按修改时间的全量同步。
- **历史**用 `git log --follow` 加页面 id 校验（每个版本里的文件头 id 必须是
  这一页的），游标是“提交加路径”，下一页从那个提交往前读，不从头走。

已知问题，带到后面：

- 改名同时内容改了一半以上，`--follow` 认不出是同一个文件，历史在那里断开。
- 有合并提交的历史里，游标翻页可能漏掉在旁支上、之后才合进来的更早版本。
- 本地克隆（`.git`）丢了不会自动重新拉：打开时报错，由管理员处理。
- 第一次取回一个很大的仓库受 `InitialTimeout`（4 分钟）限制，必须短于服务的
  响应超时。
- GitHub App、自动建仓库、第二个只推不拉的镜像、webhook 都还没做。

#### 里程碑 1.4 的现状（2026-11-21）

接口见 `docs/api.md`。定下来的、和上文不同或上文没写的地方：

- **附件的引用写成从空间根开始的路径**（`/assets/<页面 ID>/<文件名>`），不是
  3.4 节说的相对路径。相对路径在页面移动后会失效，得改正文，而正文可能正有
  草稿；从根开始的写法移动和改名都不受影响，GitHub 和 GitLab 的网页上也能
  直接显示。已有仓库里相对页面所在文件夹的写法照样能显示，规则见
  `docs/api.md` 的「Files」。
- **附件是普通文件，和页面走同一条写入路径**：本地空间进提交日志、由后台
  提交；跟随远端的空间当场提交并推送，推送被拒就撤销。文件名带内容哈希的前
  8 位，同样的内容再传一次不产生新文件。
- **读附件要登录**，响应带禁止脚本的策略；图片、音视频、PDF、纯文本在浏览器
  里直接显示，其余一律作为下载。
- **上传前的压缩**：超过 300 KB 或边长超过 2560 的 PNG、JPEG 重画成 WebP，
  小了两成以上才用；可以在浏览器里关掉（「上传原图」）。
- **快速记录的快捷键**是 Option/Alt+Shift+N。浏览器把 Ctrl/⌘+Shift 加字母
  的组合大多留给了自己，网页拦不住。
- **一个文件暂存不了不再卡住之后的提交**：`git add` 整批失败时（文件被
  `.gitignore` 或用户全局的忽略规则匹配、路径被服务器之外的东西换成了符号
  链接或设备）改为逐个暂存，服务器自己写的文件不看忽略规则；仍然暂存不了的
  那个留在提交之外。变成了目录的路径同样跳过。服务器自己不建以 `.md` 结尾的
  文件夹。
- 原文模式里上传的图片落进编辑器后，正文会由编辑器重写成统一写法（和在
  所见即所得一侧打字一样）。
- **没人引用的附件不清理**，删除页面也不删它的附件（历史版本还可能用到）。
  清理任务留到后面。
- **收件箱是一个文件夹名**，每个空间一个设置（`inbox`，默认 `Inbox`，网页上
  新建空间时用界面语言的名字）。改设置不移动任何东西。
- **卡片视图**的选择按「空间、列表种类、文件夹或标签」记在浏览器里，不写进
  `space.yml`（8.4 节说的视图配置等页面类型一起做）。摘要从 200 字加到 400 字。
- **三种编辑模式**（7.0 节）：
  - 内容只有一份（头部字段和正文），两边都是它的编辑方式。在原文一侧打字，
    正文就是那段文字，原样保存；在所见即所得一侧打字，正文由编辑器重写成
    统一写法。最后在哪一侧打字，保存的就是哪一侧。
  - **头部不是原样保存的**：原文里的头部被解析成字段后交给服务器，由服务器
    写回文件。键的顺序、没改的值的写法都保留，但注释会丢，引号和列表的写法
    可能被规整。这和 7.0 节「原文里打的字原样保留」不完全一致，只有正文做到
    了原样。原文一侧显示的头部在没改动时是文件里的原文（接口的 `header`）。
  - 头部写坏时（不是合法 YAML、`id` 被改或删掉、没有结束的 `---`）界面指出
    是哪一行；这期间正文照常保存，头部停在上一次正确的内容，不能切回所见即
    所得，左右对照里右边暂时不能编辑。写坏的原文单独存在浏览器里（它既不是
    能进编辑器的内容，也存不到服务器），关闭页面前会提示。再打开这一页时，
    或者开着的时候页面被别处更新了，这份原文不会自己接上去（页面或草稿可能
    已经在别处变了），而是放到一边，界面问你接着改还是丢弃；放到一边的可以
    有多份，互不覆盖。横幅上可以直接放弃这些改动。
  - 左右对照时另一侧在停笔后跟上（按正文长短 0.15 到 0.6 秒）；在跟上之前
    点到另一侧，会先同步再让你打字。同步只替换有变化的块，光标和正在上传的
    图片的位置不动。滚动按块对应，对不上时按比例。
  - 在原文里把正文改成编辑器自己的写法（比如把 `*` 列表改成 `-`）算改动，
    会保存；编辑器一侧则不会因为只是写法不同就认为改过。
  - 窄屏（小于 768 像素）没有左右对照。
- **编辑器的三处补强**（7.2 节）都做了：紧跟汉字的 `**粗体**` 等输入规则；
  纯文本粘贴时单个换行是段内换行、空行才分段；粘贴 Markdown 源码时解析成
  排版后的内容。

1.4 审查留下、不阻塞的已知问题：

- 浏览器的本地存储被禁用或已满时，头部没改好的原文只在屏幕上。关页面、站内
  跳转、页面在别处被更新都会先问或提示；但这时如果登录恰好失效（被踢回登录
  页），这段文字会丢。存储正常时不会。
- 原文一侧的头部按数据保存，注释和引号写法不保留（上文已述）。
- 在原文模式里恢复历史版本后点撤销，放回的是规整过的 Markdown。
- 页面内容被整体替换时（别处更新、冲突里选对方、恢复历史版本），正在上传的
  图片的落点可能跑到文末。
- 从本地草稿把已删除的页面找回来时，没改过的其它头部字段不带回来。
- 上传一个文件要整个读进内存再写盘；上限最多 256 MiB。
- 快速记录在两个标签页同时保存、或请求成功但回应丢了时，可能存出两篇。
- 左右对照里，窄窗口下工具栏最右边的按钮会被截掉。
- 快速记录的快捷键、IME 输入、真实的文件选择框没有人手测过。

    现在的单用户模式（`serve --space`）就是只有核心的形态，要一直能跑、
    一直在测试里。
  - 多人的部分（账号、空间成员、角色、管理后台、以后的注册和配额）是叠在
    核心上面的一层，只通过「谁在请求、对这个空间有哪些权限」这一个接口
    和核心打交道。新功能先在单用户模式下成立，再加权限。
  - 前端同理：管理后台、成员、账号设置是可以整块不加载的部分；单用户时
    界面里看不到它们的入口。
- **多种登录方式**（所有者 2026-11-22，后期）：现在只能配一个 OIDC 提供方。
  以后要能同时配多个，登录页每个一个按钮，账号的「安全」里逐个关联和解除。
  Google 和微软（Entra ID）是标准 OIDC，主要是把「一个」改成「多个」；
  GitHub 不是 OIDC（没有 id_token，要用它的 OAuth 和用户接口），需要单独
  写一个适配。同一个邮箱从不同提供方登录时不自动合并账号，除非该提供方
  声明邮箱已验证并且管理员开了这个选项。
- **多租户和公开注册**是再往后的阶段，以共享空间为前提：注册开关、邮件
  （验证和找回密码）、每人的配额、防滥用、数据隔离强度的重新评估、条款和
  隐私说明。加密空间也在那之后。

**1.7 做什么、不做什么**（2026-11-22 定）：做共享空间、权限项、成员管理、
按人记的提交作者、管理后台和单人形态的拆分。多种登录方式、组、注册、配额、
加密空间不在 1.7。

**实现方案**（2026-11-22）：

- **权限项，不比较角色名**。一个包里定义权限项：`read`（看页面、历史、
  附件、搜索）、`write`（建、改、移动、删页面和文件夹，标签，附件，导入，
  草稿）、`members`（管成员）、`manage`（改名、收件箱、远端和同步、重建
  索引）。角色是权限项的集合，只在这一张表里定义：所有者 = 全部，可编辑 =
  `read`+`write`，只读 = `read`。以后的自定义角色就是这张表多几行。
- **接口只认「谁、对这个空间有哪些权限」**。每个路由声明它要的权限项，
  `api` 的 `handle` 是唯一做决定的地方：不是成员（管理员除外）一律 404，
  是成员但缺这项权限 403 `no_permission`（单独的错误码，不与跨站拒绝的 `forbidden` 混在一起）。核心（`space` 包）不知道账号和角色，只多收一个
  「这次改动算谁的」。单人模式下唯一的本地用户拥有全部权限，不走成员表。
- **判断不查库**：成员关系照旧按人缓存在内存里，一次请求的权限判断是查
  一张小表；成员变动时只作废涉及的那几个人的缓存。
- **管理员能看全部**：管理员对任何空间都有全部权限，但不算成员，自己的
  空间列表里不出现别人的空间；要进别人的空间从管理后台点进去。
- **成员管理**（需要 `members`）：按用户名加人并给角色、改角色、移除；
  成员可以自己退出。空间至少留一个所有者。个人空间只能有本人，不能共享。
- **提交按人记作者**：每次改动带上做改动的人，提交时按作者分组，一次提交
  只含一个人的改动；作者是这个人，提交者仍是服务。日志里的记录也带作者，
  崩溃恢复后的提交作者不丢。跟随远端的空间本来就一次改动一次提交，直接用
  这个人。代价：同一个空闲窗口里两个人都改了，会是两次提交而不是一次。
- **管理后台**（只有管理员；单人模式下这些接口不存在）：
  - 用户和邀请：接口不变，界面从设置搬到 `/admin`。
  - 所有空间：名称、是不是个人空间、所有者、成员数、大小、同步状态、是否
    停用。一次查询带出所有者和成员数。**大小不在列表时现算**：几万篇的
    空间每次遍历太贵，改成后台慢慢算好存进状态库（每个空间最多几小时算
    一次，一次只算一个），列表只读存好的值，单个空间可以手动重算。
  - 转移所有权：新所有者成为所有者，原所有者降为可编辑。个人空间不能转移。
  - 停用和恢复：停用的空间仍在成员的列表里（带标记），但打不开、改不了；
    已经打开的会被关掉。
  - 删除：先关掉，数据库里的记录删掉，目录**移进 `数据目录/trash/`**，
    不当场删文件，误删还能从磁盘找回。个人空间在本人还在时不能删。
  - 服务器状态：版本、运行时长、数据库类型、空间和用户数、打开着的空间数、
    数据目录所在磁盘的剩余空间。
- **前端**：空间信息带上自己的角色和权限项，只读成员看不到新建、删除、
  拖拽这些入口，编辑器只读。空间设置里多一个「成员」分区。管理后台在
  `/admin`，单独一个按需加载的块，只有管理员会加载；单人模式下成员、账号、
  管理后台的入口都不出现。

**1.7 的现状（2026-11-22）**：上面的方案都做了，接口见 `docs/api.md` 的
「Members」和「Administration」。实现时定下来的、方案里没写的：

- 权限项在 `internal/perm`，一个字节的位集合；路由在 `internal/api/routes.go`
  里声明要的权限项，缺权限答 403，错误码是 `no_permission`（和跨站拒绝的
  `forbidden` 分开，前端按码区分）。
- 成员关系的缓存带代数，成员变动前读到的列表不会在变动后被存进缓存；移除的
  成员下一个请求就被拒绝。最后一个所有者的判断在事务里锁住空间那一行，只算
  能登录的所有者。
- 提交按人记作者：作者换人时，先把前一个人待提交的改动提交掉，再写这个人的
  改动，所以一次提交只含一个人的改动，交错编辑时提交会多一些（每换一次人一次
  提交）。
- 草稿的自动写入先查作者现在还能不能写这个空间：被移除或降为只读的人的草稿
  留着、不写入、10 分钟后再看，恢复权限后照常写入；自己的草稿只读成员也能
  丢弃。删除空间时，所有人的草稿先存成 `trash/<id>-<时间>.drafts.json`。
- 停用的空间仍在成员列表里，打不开；成员可以退出停用的空间。
- 管理员查看别人的空间时，前端按 id 取这一个空间（`GET /api/admin/spaces/{id}`），
  不翻整个列表；转移所有权的选人框按用户名或名字搜索，只列可用的账号（`GET /api/users?q=&enabled=1`）。
- 管理后台的界面、文字和接口调用在单独的按需加载块里，非管理员不加载。
- 浏览器里实测过：只读成员看到「只读」标记、编辑器不可编辑、没有新建和删除；
  管理后台三页；管理员按地址打开别人的空间只发一个请求。

已知问题，带到后面：

- 两个人交替保存同一个空间时，每次换人都要等一次 Git 提交（约 60 毫秒），
  期间这个空间的其他写入排队；Git 卡住会挡住这个空间的写入。
- 删除失败（`os.Remove` 出错）时，这个路径上别人先前的改动会记到删除的人
  名下；崩溃只在一个很窄的时间窗里会让某个路径的作者记错。都不丢内容。
- 提交后的日志改写可能丢掉「已记日志、还没交给提交器」的记录（1.6 之前就有），
  崩溃时那次改动要等下次碰到这个文件才提交。
- PostgreSQL 上空间名搜索的大小写不敏感只对 ASCII 可靠（C 区域设置的库）。
- 管理员把自己移出一个空间后，按地址仍能以管理员身份打开它。

**2.1 页面类型、属性面板、表格视图**

- 类型是 `.petalbook/types/<名字>.json`，标准 JSON Schema，只用其中一个
  子集：字符串、长文本、单选（`enum`）、多选（`array` + `enum`）、日期、
  数字、勾选、网址。子集之外的关键字照样留在文件里，界面上该字段按原始
  YAML 显示和编辑，不丢、不报错。
- 文件夹在 `space.yml` 里绑定类型，子文件夹继承，可以单独改绑；页面头部
  写了 `type` 的以头部为准。
- 属性面板由 schema 生成，放在副标题和标签下面。不引入 rjsf：它为通用后台
  表单设计，体积大，而这里只要上面几种控件；自己写一个小的渲染器，单独
  按需加载，没有类型的页面不加载。
- 空间设置里有「类型」分区：新建、改字段、删字段。改名或删掉一个字段不去
  改已有页面的头部（几万篇一次全改既慢又是一次巨大的提交），旧字段在属性
  面板里显示为「不在类型里」，可以一键清掉单篇。
- **索引**：新加一张 `props(page, key, value)` 表，按 `(key, value)` 和
  `page` 各建索引。单选、日期、数字存成可排序的形式，多选每个值一行。表格
  视图的筛选和排序都在这张表上做，不读文件。几万篇时先用一个 5 万篇的造数
  测一次筛选加排序的耗时再定方案，目标和现在的列表一样在几十毫秒内。
- **表格视图**：绑定了类型的文件夹可用。列是类型字段加标题、标签、时间；
  按列排序，按字段筛选；单选、多选、日期、勾选在格子里直接改（改的是页面
  头部，走正常的草稿和提交，一次改一篇）。行数多时分页加载并虚拟滚动，不
  一次拿全部。
- 单用户模式、只读成员（格子不可改）都要测到。

2.1 的实现方案（2026-11-22）：

- **类型文件**：`.petalbook/types/<名字>.json`，文件名（不含 `.json`）就是
  页面头部 `type` 的值，建好后不改名（改名要动所有页面）；显示名是 schema
  的 `title`，可以改。顶层是 `{"title", "properties": {…}}`，字段顺序就是
  文件里 `properties` 的键顺序（读时保持顺序，不经过 Go 的 map）。
- **字段种类**和 schema 的对应：
  | 种类 | schema |
  |---|---|
  | 文字 | `{"type":"string"}` |
  | 长文字 | `{"type":"string","x-multiline":true}` |
  | 单选 | `{"type":"string","enum":[…]}` |
  | 多选 | `{"type":"array","items":{"type":"string","enum":[…]},"uniqueItems":true}` |
  | 日期 | `{"type":"string","format":"date"}` |
  | 数字 | `{"type":"number"}` |
  | 勾选 | `{"type":"boolean"}` |
  | 网址 | `{"type":"string","format":"uri"}` |
  每个字段可以有 `title`（显示名）。认不出的字段种类为「其他」，属性面板里按
  原始 YAML 显示和编辑。服务端改类型时只改它认得的键，字段对象里其余的键
  原样留着。
- **字段的键**：不能是内置字段（`id`、`title`、`subtitle`、`source`、`tags`、
  `created`、`type`）和预留的 `publish`、`slug`；非空，不超过 64 字节，没有
  控制字符和 `:`。可以是中文。
- **绑定**写在 `space.yml`：
  ```yaml
  folders:
    Tang:
      type: 文案
  ```
  子文件夹继承最近的绑定；页面头部写了 `type` 的以头部为准。新建页面时**不**
  往头部写 `type`，靠继承；页面响应和摘要里多一个 `effectiveType`。绑定按路径
  记，所以文件夹改名、移动时同一次提交里改 `space.yml`。
- **索引**：`pages` 表多一列 `props`（头部里内置字段以外的键，JSON，过长的
  字符串截到 300 字）；新表 `props(page, key, pos, val, skey)`：标量一行，
  数组每个元素一行（`pos` 是位置），对象不进。`skey` 是排序用的键：数字编码
  成按字面能排序的文本，日期原样，文字同 `title_key` 的规则，勾选 0/1。
  索引 `(key, skey, page)`、`(key, val, page)`、`(page)`。索引所有非内置的键，
  不管属于哪个类型，所以改类型、改绑定都不用重建索引。索引版本加一，第一次
  启动会全量重建一次（5 万篇约 30 秒）。
- **列表接口**：`GET …/pages` 加：
  - `props=1`：摘要里带 `props`（上面那列）和 `rev`，表格视图用；不带时摘要
    不变，列表和卡片的流量不增加。
  - `sort=prop:<键>` / `-prop:<键>`：按字段排序，没有这个字段的排最后，再按
    `rowid`；多选按第一个值。游标照旧是键集分页。
  - `filter`：JSON 数组，每项 `{"key","op","values"}`，`op` 是 `in`（等于其中
    之一；多选是包含其中之一）、`range`（`values` 是 `[从, 到]`，任一端可为
    空，数字和日期用）、`empty`、`notEmpty`、`contains`（文字包含，按
    `val` 做子串，只在这个键的行里找）。多项之间是「且」。
- **只改属性的接口**：`PATCH …/pages/{id}/props`，`{"baseRev", "set": {…},
  "unset": [...]}`，只改头部，正文不经过网络；`baseRev` 不对答 409，同 PUT。
  需要 `write`。表格格子里的修改走它。草稿的处理和 PUT 一样（不丢草稿）。
- **类型接口**（读要 `read`，写要 `manage`）：
  - `GET …/types`：每个类型的名字、显示名、按顺序的字段（键、显示名、种类、
    选项、原始 schema），加上文件读不了时的错误说明；外加所有绑定。
  - `PUT …/types/{name}`：建或改，带字段列表；服务端合并进原文件，保留认不出
    的键。
  - `DELETE …/types/{name}`：删文件，并在同一次提交里去掉指向它的绑定。页面
    头部不动。
  - `PUT …/folders/type`：`{"folder", "type"}`，`type` 为空是解除绑定。
  类型文件写坏了（手改）就照 `tags.yml` 的做法：不覆盖，答 400 说要手修。
  一个空间最多 100 个类型，每个文件最多 256 KiB、200 个字段。
- **值的校验**：不拦保存。不符合 schema 的值照样存，属性面板标红；2.5 的
  校验页列出来。
- **前端**：
  - 属性面板在副标题、标签下面，按字段种类给控件；值的修改进草稿，和标题
    一样。面板是单独的按需加载块，页面没有类型时不加载。不在类型里的字段
    另列一组，每个可以清掉。
  - 空间设置多一个「类型」分区（有 `manage` 才能改）：建类型、加字段、改
    显示名、改选项、调顺序、删字段、删类型；文件夹的右键菜单里有「设置
    类型」。
  - 文件夹视图多一个「表格」，有类型的文件夹才出现。列是标题加类型字段，
    再加标签、更新时间；点列头排序；字段筛选；单选、多选、日期、勾选、
    数字在格子里改（只读成员不能改）。按游标分批加载，滚到底再取下一批，
    行用虚拟滚动，几千行也不卡。
  - 选的视图（列表、卡片、表格）按文件夹记在浏览器里；2.2 再改成存进
    `space.yml`。

**2.1 的现状（2026-11-22）**：上面的方案都做了，接口见 `docs/api.md`。实现时
定下来的、方案里没写的：

- 实测（5 万篇在一个文件夹里）：按字段排序取一页约 0.3 毫秒，翻到第 400 页
  也一样；筛选加排序 1 到 2 毫秒；最慢的是只命中很少几篇的范围筛选，约 40 到
  60 毫秒。
- 一篇最多索引 200 个字段，一个列表最多 100 项；空文字和空列表算没有这个
  字段，按字段排序时排在最后。索引里存的值不完整（截断、对象、超出上限）时，
  摘要的 `partialProps` 列出这些键，表格里这些格子只读，要打开页面改。
- 类型带 `rev`，改和删都要带上读到的 `rev`，别人先改了就答 409，不会互相
  覆盖。已有字段即使不符合新字段的命名规则也照样保留。
- 文件夹移动、删除时，改目录和改 `space.yml` 的绑定记成一笔日志，崩溃后恢复
  时一起做完；本地模式下绑定写不进去就把移动撤回。`space.yml` 只有注释时，
  写绑定不会丢注释；同一个文件夹写了两条绑定时，以最后一条为准。
- 头部里真的是日期的文字（`YYYY-MM-DD`）不加引号写，其余像日期的文字加引号，
  从不写 `!!` 标签，别的 YAML 工具读得了。
- 表格里的数字和文字格子在离开或按回车时才保存，Esc 取消；选择类的格子
  点了就存。
- 浏览器里实测过：表格的排序、格子里改值后文件和提交都对；属性面板的各种
  控件、不在选项里的值标红保留、「不在这个类型里」一组；设置里的类型编辑和
  文件夹绑定。

已知问题，带到后面：

- 按单选字段排序是按文字排，不是按选项的顺序（「修改中、定稿、草稿」而不是
  「草稿、修改中、定稿」）。按选项顺序排要么每次查询现排（几万篇时慢），要么
  改选项顺序时重算所有相关页面的排序键；放到 2.2 和保存的视图一起定。
- 改字段的选项（改名、删掉一个选项）不会改已有页面里的值，旧值在属性面板和
  表格里标红；批量改值以后再做。
- 文字「包含」筛选只对 ASCII 字母不分大小写。

**2.2 保存的视图、看板、连读**

- 视图 = 筛选、排序、分组、展示方式的组合，存在 `space.yml` 的 `views`
  里，按文件夹（或标签）记，可以有多个，有一个默认的。
- **看板**：按一个单选字段分列，拖动卡片改值；每列分页加载，不一次拉全部
  卡片。
- **连读**：把一个文件夹或一组筛选结果按顺序排成一篇长文阅读，往下滚时
  按批取正文；只读，点某一篇进入编辑。
- 列表、卡片、表格、看板、连读在标签页和搜索结果上也能用。

2.2 的实现方案（2026-11-22）：

- **视图存在哪**：文件夹的视图写在 `space.yml` 里这个文件夹的条目下，和绑定
  放在一起，文件夹改名、移动、删除时随条目一起走（沿用 2.1 的日志和恢复）：
  ```yaml
  folders:
    文案:
      type: wenan
      views:
        - id: k3f9
          name: 按状态
          layout: board
          group: status
          sort: -prop:written
          filter: [{key: series, op: in, values: [冬季]}]
  ```
  标签的视图写在 `tags.yml` 这个标签的条目下（和颜色在一起）。根目录的键是
  `""`。
- **一个视图**：`id`（服务端发，短随机串，空间内唯一）、`name`、`layout`
  （`list`、`cards`、`table`、`board`、`read`）、`sort`、`filter`（同列表接口的
  写法）、`group`（看板的分列字段）、`hidden`（表格里隐藏的列）。第一个视图是
  默认视图。认不出的键原样保留。每个文件夹或标签最多 20 个视图。
- **接口**：`GET …/views?folder=` 或 `?tag=`，返回视图列表和 `rev`；`PUT …/views`
  带 `{folder 或 tag, baseRev, views}`，整列替换，`rev` 不对答 409（带 `current`）。
  改视图要 `write`：视图是大家共用的排列方式，能写页面的人就能改。没有写权限
  的人可以切换视图，也可以临时改排序和筛选，只是存不回去。
- **前端**：文件夹页和标签页顶上一排视图标签；新建、改名、复制、删除、拖动
  排顺序。在一个视图里改了排序、筛选、分列、隐藏的列，标签上出现「已修改」，
  点「保存」才写回（不是每点一下就提交一次）；「还原」丢掉改动。每个文件夹
  上次用的视图记在浏览器里。还没有存过视图的文件夹和现在一样（一个隐含的
  默认视图）。2.1 存在浏览器里的列表、卡片、表格的选择作为隐含视图的起点。
- **单选按选项顺序排**（2.1 遗留）：按字段排序、并且列表带了 `folder` 时，
  如果这个字段在文件夹的类型里是单选（或多选，按第一个值），排序顺序是：
  选项依次，然后不在选项里的值（按文字），最后没有这个字段的。实现上按组做
  索引扫描（每个选项一组，用 `(key, val, page)` 索引），游标记着在第几组，
  不做全表排序。和 2.1 一样用 5 万篇的造数测，目标在几十毫秒内。
- **看板**：`group` 是一个单选字段。列依次是各个选项、「其他值」（不在选项里
  的值，有才显示）、「空」。
  - 每列单独分页：列表接口加筛选 `notIn`（有值且不在给的选项里），各列就是
    `in [选项]`、`notIn [全部选项]`、`empty` 三种筛选，每次 20 张，滚到底再取。
  - 列头的数量：新接口 `GET …/pages/groups?folder=&key=&filter=`，返回
    `[{value, count}]` 加空值的数量；在 `props` 表上按值分组计数，不读文件。
  - 卡片显示标题（没有标题的显示正文开头）、两行摘录、标签、视图里选的至多
    3 个字段。拖到别的列就是改这个字段（拖到「空」是去掉它），走 2.1 的
    `PATCH props`，带 `rev`，冲突时刷新这张卡并提示。列内的顺序跟视图的排序，
    不能手动排（第一版不做手动排序）。只读成员不能拖。
- **连读**：按视图的排序和筛选，把页面一篇接一篇排成长文。
  - 列表接口加 `body=1`：摘要里带正文（Markdown），这时 `limit` 最多 20。
    要读这么多个文件，所以只在连读用。
  - 前端把正文渲染成只读的排版，**不**为每篇挂一个编辑器；用已有的
    Markdown 解析得到文档再画成静态的 HTML（图片、表格、代码、mermaid 和
    编辑器里的样子一致）。是单独的按需加载块。
  - 每篇显示标题、副标题（文案类型照 `《标题》｜副标题` 的样子），没有标题
    的直接是正文；点标题进入编辑。往下滚时按批取，离开视口很远的篇目从
    页面上卸掉，几百篇也不卡。
- **标签页**能用除表格以外的全部展示方式（标签下的页面不一定同一类型）；
  标签页的看板只有在视图里选了分列字段时才有。搜索现在是对话框，不做视图。
- 顺手修 2.1 时发现的：表格的菜单开着时整张表被替换，改对齐会报错（
  `tableOps.ts` 的 `columnAlign`）。

**2.2 的现状（2026-11-23）**：上面的方案都做了，接口见 `docs/api.md`。经过
十一轮对抗式审查，实现时定下来的、方案里没写的：

- **原则（所有者定）**：系统层面的问题不交给用户修。设置文件（`space.yml`、
  `tags.yml`、类型文件）读不了时，从 Git 历史里最近能读的版本恢复，能救的
  条目逐个救回，下次写入时修好并把原文留成 `<文件>.unreadable-<时间>`，只给
  管理者一条通知；`.petalbook` 或 `.petalbook/types` 被换成链接时挪开重建，
  绝不跟进去。
- **YAML 锚点和别名**：读时照常解析（每个锚点只解析一次，开销只看文件写了
  多少），写时只复制要改的那段、改完核对其余别名的意思没变；服务器自己只在
  一种情况下写别名（给很多文件夹共用的条目去掉类型时）。
- **服务器自己的状态**（索引、日志、通知、单用户模式的草稿库）从
  `.petalbook/cache` 挪到 Git 目录里（`.git/petalbook-state`，worktree 用它
  自己的 Git 目录），打开时只搬服务器自己的、没被 Git 管的文件；`.petalbook/`
  以后只放仓库内容。写文件时临时文件放在目标旁边（`.petalbook-w-*`）。
- **索引的查询**：每个条件（范围、标签、筛选）都能按页查也能按索引区间取，
  每次从三种做法里挑最省的；一个请求只读一个快照（读事务，加一个版本号判断
  并行查询是否同一时刻）；写入有自己的连接；WAL 超过 16 MB 时在读之间合并，
  不会无限变大。加锁顺序写在 `internal/index/read.go` 开头。
- **实测**（5 万篇）：API 允许的组合基本都在 100 毫秒以内；按选项顺序排序、
  看板每列、看板计数多在几毫秒到几十毫秒。
- **视图的「没保存的改动」**：一份工作副本，排序也在里面；改动只落在它所属的
  视图上，不是本人的操作就不悄悄丢（会提示）；本人保存视图的那一下视图控件
  锁住，保存后重新读一次列表，读失败就先用保存的回复。
- 看板卡片可以用键盘「移动到…」；管理者在空间设置和顶部提示里看到设置文件
  的恢复通知。
- PostgreSQL 上也跑一遍契约测试（`make contract-postgres`，在 `check-full`
  和 `main` 的 CI 里）。

已知问题，带到后面：

- 同时用满 10 个标签和 10 个几乎不筛掉页面的筛选时，查询和计数约 95–150
  毫秒；写入一直不停时会退回按顺序读，可能接近 200 毫秒。
- 读请求很多（20 个以上一直不停）时，最慢的一次读约 250–330 毫秒，主要在排队
  等 8 个读连接。
- 1 万个文件夹用合并键（`<<: *模板`）共用一个模板时，给它们去掉类型若写出来
  超过 1 MB 会被拒绝。
- 文件有语法错误时，引用了别处锚点的条目算作丢失（列在通知里），没有救回。
- 一次全套检查（`make check-full`）约 7–8 分钟，太慢；2.2 合并后单独提速。

**2.3 空间首页、收藏、每日文案**（所有者 2026-11-22 提出）

- **每个空间一个首页**（所有者定，不做跨空间的总首页），是进入空间后默认
  打开的页面，地址 `/s/<空间>/`。从上到下：
  1. **问好和每日文案**（所有者 2026-11-23：每日文案放最上面，和问好在
     一起）：按浏览器时间说「早上好／下午好／晚上好，<名字>」，下面紧接着
     是今天的文案（文案类型照 `《标题》｜副标题` 的样子），可以「换一条」，
     点开进入编辑；没有设置来源时只有问好。
  2. **快速记录**：首页上直接写一条，写完进这个空间的收件箱。
  3. **继续写**：最近更新的 5 到 8 篇。
  4. **收件箱**：还没归类的条数和最前面几条，带「去整理」。
  5. **收藏**：自己收藏的页面、文件夹和视图。
- **每日文案**：
  - 从哪里抽在空间设置里选：一个文件夹、一个标签或一个类型（可以加筛选，
    比如只抽「定稿」的）。没选时这一块不出现。设置存在 `space.yml`，大家
    看到同一条。
  - 同一天、同一个空间抽到的是同一篇：用日期（按浏览器所在时区，作为参数
    传给服务端）和空间 ID 算出一个序号，在符合条件的页面里按序号取。数和
    取都走索引（一次计数加一次按偏移取一条），不读别的文件。
  - 「换一条」随机再取一篇，只在自己的浏览器里，不改别人看到的。
- **收藏**是每个人自己的，存在状态库（不进仓库，不提交），按空间分；可以
  收藏页面、文件夹、视图，能拖动排序。页面删除或被移出空间后，收藏里显示为
  失效，可以清掉。单用户模式同样有（状态库本来就在）。侧栏也有「收藏」一组。
- 首页每一块都只取前几条，查索引；首页一共几个请求，不随页面数增长。
- **问好要有点意思**（所有者 2026-11-23）：不只是早上好／下午好／晚上好。
  完全在浏览器里算，不发请求，按界面语言（中文、英文，以后加的语言各有
  一套）从一组句子里挑：
  - 按时段细分：清晨、上午、午后、傍晚、深夜（如「夜猫子，还在写呀」）、
    凌晨（「天快亮了，记得睡一会儿」）。
  - 按日子：周一、周五、周末；节日和节气（元旦、春节、清明、端午、中秋、
    冬至等农历和节气用一张按年预先算好的小表，覆盖往后十年）；用户的
    注册纪念日。
  - 按情形：今天第一次打开、好久没来（「好久不见」）、刚写完一篇回到首页、
    今天已经写了好几篇。
  - 同一种情形有几句，按日期轮换，同一天里不跳来跳去；也可以在偏好里关掉
    花样，只用简单的问候。
  - 句子写在 i18n 文件里，好改好加，不写死在组件里。
- **每日文案的来源，三层**（所有者 2026-11-23：「都要」）：
  1. 空间自己的（上面的 `daily`）。
  2. **管理员配的全站默认**：管理后台「每日文案」页，可选一个空间里的
     文件夹、标签或类型，或者直接粘贴／上传一批（一行一条，或一个 Markdown
     文件，存在状态库）。空间没设置时用它；所有者可以在空间里关掉。选一个
     空间做全站来源时明确提示「这些内容会展示给所有人」。
  3. **自定义外部接口**：管理员填网址和字段映射（正文、出处、作者的 JSON
     路径），可以按语言填不同的接口（网址里可以用 `{lang}`），比如中文用
     一言（hitokoto），英文用 ZenQuotes。服务端去取，每个接口每天取一次并
     缓存，大家看到同一条；「换一条」再取，有频率上限。防服务器被用来访问
     内网：只允许管理员列出的主机，不连内网和本机地址（解析后再检查，防
     DNS 重绑定），超时 5 秒、响应最多 64 KB、只接受 JSON；取不到时这一块
     不出现，不影响首页。空间所有者可以选用管理员配好的接口，但不能自己填
     网址。
  - 优先级：空间自己的 > 空间选用的外部接口 > 全站默认。都没有时只显示
    问好。
  - **范围**（所有者 2026-11-23 确认）：管理员配的全站默认（贴的文案、
    选作来源的空间）和外部接口是整台服务器共用的，所有用户、所有空间一样；
    外部接口按（接口，语言，刷新周期）缓存，所以同一周期里用同一接口、同一
    语言的人看到同一条。空间自己的来源只在这个空间里有效，内容也只给这个
    空间的成员看。以后做多租户和公开注册时，在全站默认之下加一层「每个租户
    的默认」，优先级插在空间和全站之间。
  - **多语言**：文案跟着界面语言走。空间来源可以按语言分（比如
    `daily: {zh: {folder: 文案}, en: {tag: quotes}}`，只写一种就所有语言都用
    它）；全站的一批文案可以标语言；外部接口按语言各配一个。某种语言没有
    时退回到有的那种。
  - **按语言配置，代码和界面都支持**：语言是一张表，不写死中文、英文；
    界面上空间设置的「首页」分区和管理后台的「每日文案」页，都按语言分
    标签页（「所有语言」一页加每种语言一页），每页可以选来源、贴文案、选
    外部接口；以后界面多一种语言，这里自动多一页。
  - **内置的外部接口预设**（2026-11-23 核对过各家文档）：随程序带着，默认
    **不启用**（自托管的服务不应在管理员没同意时自己去连外网），管理员点一下
    启用，主机自动加入允许名单：
    - 中文：一言国际线路 `https://international.v1.hitokoto.cn/`（文档写 QPS
      20，含 2 秒缓存；普通线路 `v1.hitokoto.cn` 只有 2）。免费、不要密钥，
      公益服务；恳请带回链 `https://hitokoto.cn?uuid=<uuid>`，所以显示时
      带「来自一言」的链接。默认 `max_length` 30，预设里调到 80。正文
      `hitokoto`，出处 `from`，作者 `from_who`。预设的速率上限填 20。
    - 英文：Quotable `https://api.quotable.io/quotes/random`（MIT 开源、不要
      密钥，文档写每个 IP 每分钟 180 次）。正文 `[0].content`，作者
      `[0].author`。预设的速率上限填 3（每秒）。
    - 没有选 ZenQuotes 做默认：免费版每 30 秒只能 5 次，并且必须显示回链。
    - 想完全不受限：Quotable 和 QuoteSlate 都是 MIT 开源，可以自己部署一份，
      在后台照预设填自己的地址。
    - 服务器统一取并缓存，每个周期只请求一次，正常使用远低于这些上限。
    - **回链**：接口可以配一个「出处链接」模板（如一言的 `uuid`），显示在文案
      下面；预设里填好。
  - **管理员完全自己配置接口**（所有者 2026-11-23 强调）：预设只是起点，
    管理员可以新建、改、删任意多个接口，每个接口：
    - 名称、语言（或「所有语言」）、网址（`GET`，可用 `{lang}`、`{date}`）；
    - 请求头（比如 `X-Api-Key: …`），值加密存库，界面上只显示「已保存 ·
      更换」；
    - 正文、出处、作者的 JSON 路径（如 `hitokoto`、`[0].q`、`data.content`），
      正文必填；
    - **刷新频率**（所有者 2026-11-23）：大家看到的那一条多久换一次——
      每天（默认）、每小时、每 N 分钟；「换一条」是否每次都向对方要新的；
    - **对外请求速率上限**：每秒最多几次（令牌桶，比如一言国际接口可以填
      20），所有用户的请求合起来不超过它；超了就用缓存里的一条，不排队等；
    - 「试一下」按钮：立即请求一次，显示原始返回（截断）和按路径取出的
      结果，路径错了当场看得到；
    - 启用／停用。
    保存时把网址的主机加入允许名单；内网、本机地址始终不允许。
  - **服务器统一取、再分发，并且缓存**（所有者 2026-11-23）：浏览器从不
    直接请求外部接口。理由：密钥不出服务器；每个接口每天只请求一次，不会
    因为人多被对方限流；所有人看到同一条；不受对方跨域设置影响；内网防护
    只需要在一处做。缓存分三层：
    1. **服务器内存**：按（接口，语言，刷新周期，skip）记住结果，周期内直接用。
    2. **状态库**：同样的结果写进状态库（只留最近 7 天），服务重启后不用再
       请求；多个进程或以后多实例时也共用。
    3. **浏览器**：`GET …/daily` 带 `Cache-Control`（到当天结束为止，按请求
       里的日期算），同一天反复打开首页不再请求服务器；「换一条」的结果只
       缓存在页面里。
    外部接口失败时用最近一次成功的结果（标明是哪天的），再失败才不显示；
    失败后按指数退避重试，不会每次打开首页都去敲对方。空间来源和全站文案
    的结果也走第 1、3 层缓存（它们本来就只查索引，很便宜）。

2.3 的实现方案（2026-11-23）：

- **首页**：地址 `/s/<空间>/`，进入空间（包括登录后、切换空间后）默认打开
  它，原来的「最近」仍在侧栏。首页只拼已有和新加的几个小接口，一共不超过
  5 个请求：
  - 快速记录：沿用现有的快速记录接口，首页上直接是一个输入框，写完清空并
    提示「已放进收件箱」，收件箱那一块随即刷新。
  - 继续写：`GET …/pages?sort=-updated&limit=8`（已有）。
  - 收件箱：条数取自文件夹树里收件箱那一行的计数（已有，O(文件夹数)），最前
    面 5 条用 `GET …/pages?folder=<收件箱>&limit=5`。

  - 只读成员看到的首页没有快速记录。单用户模式同样有首页。
- **每日文案的来源**写在 `space.yml` 顶层：

  ```yaml
    folder: 文案        # 或 tag: … 或 type: …，三选一
    filter: [{key: status, op: in, values: [定稿]}]   # 可选，同列表接口
  ```

  空间设置新加的「首页」分区里选。

  - 服务端用 `hash(空间 ID, date)` 加上 `skip` 算出序号 n，在符合条件的页面
    里取第 n 篇（`n mod 总数`）：一次带条件的计数加一次按 `rowid` 排序、偏移
    n 的读取，都走索引；用 5 万篇的造数测，目标几十毫秒内。

    不会让大家看到的那一条变来变去；那一篇被删了才重新取。

  created)`，`kind` 是 `page`（target 是页面 id）、`folder`（路径）、`view`

  PostgreSQL 各一个迁移，两边都要测。

    每项带显示名和 `missing`（页面不在了、文件夹不在了、视图不在了）；

    读文件。
  - 文件夹改名、移动时，收藏里的路径跟着改（和绑定一样随文件夹走，但收藏在
    状态库里，所以在移动成功后由服务端更新这个空间里所有人的这一项）。

  `name_key`，存 Go 里做的 Unicode 大小写折叠（`cases.Fold`）结果，搜索

  语 İ 等。
- **前端**：首页是一个按需加载的块；每日文案那块在没有来源时不请求；收藏的
  拖动排序沿用视图标签的做法，并有键盘「上移/下移」。文字中英文齐全。
- **测试**：后端单元测试（每日文案的确定性、跨日、`skip`、删页后重取、筛选；

**2.4 页面链接和反向链接**

- 编辑器里输入 `[[` 弹出页面选择（走现有搜索接口），选中后插入一个链接；
  链接显示为目标页面当前的标题，点击打开。
- **链接在文件里的写法**（所有者 2026-11-22 定）：标准的相对路径链接，目标
  的 `id` 放在链接的标题位置：`[暮雪](../Tang/暮雪.md "01JD3K8Q7Z")`。
  - 在 GitHub 和别的编辑器里照常能点，`id` 只在悬停时显示。
  - 在 PetalBook 里改名或移动一篇时，同一次提交里改掉所有链到它的文件的
    路径；这些文件从 `links` 表查出来，不扫磁盘。
  - 在外面直接改名或移动的，fetch 到改动后按 `id` 找到新位置，自动改回
    链接的路径（作为服务的一次提交）；找不到的在校验页列为断链。
  - 链接标题只有恰好是一个 `id` 时才当作 `id`；别的标题文字原样保留，
    这种链接只按路径认。
  - 只写路径、没带 `id` 的链接（手写或从别处导入的）照样认，按路径解析；
    PetalBook 下次保存这篇时补上 `id`。
  - 以后链到某个小标题用 `#锚点`，和 `id` 不冲突。
  - 编辑器里的显示文字是写进文件时的标题；目标改标题后，链接文字不自动
    改（改别人的正文要谨慎），反向链接和悬停提示里显示新标题。
- **索引**：新加 `links(src, dst)`，两个方向都建索引；保存一篇时只重算这一
  篇的出链。反向链接、断链都从这张表查，不扫文件。
- 右栏「反向链接」：哪些页面链到了这一篇，带上下文摘录。
- 页面被删除后，指向它的链接在编辑器里标成断链，不自动改别的文件。

2.4 的实现方案（2026-11-23）：

- **认链接**：页面正文里的 Markdown 链接，目标是空间内的相对路径（`.md`
  结尾，可带 `#锚点`），或标题恰好是一个页面 `id`。外链、图片、附件不算。
  代码块和行内代码里的不算。解析用服务端已有的 Markdown 解析（goldmark），
  和编辑器的转换层对同一组用例的结果要一致（加到往返测试里）。
- **索引**：`links(src INTEGER, dst_id TEXT, dst_path TEXT, anchor TEXT,
  text TEXT, pos INTEGER)`；`dst_id` 有就用它，没有就按路径解析到 id，解析
  不到的 `dst_id` 为空、记为断链。索引 `(dst_id)`、`(dst_path)`、`(src)`。
  建索引和每次保存时只重算这一篇的出链。索引版本加一（第一次启动重建一次）。
- **接口**：
  - `GET …/pages/{id}/backlinks?cursor=`：链到这一篇的页面，带链接所在的那
    一段摘录（只读这几个来源文件，分页每次 20 个）。
  - `GET …/pages/{id}/links`：这一篇的出链，每个标明目标现在的标题、是否
    断链（编辑器标断链、悬停提示用）。
  - 页面选择沿用现有搜索接口。
- **改名和移动时改链接**：`space` 包里改名、移动页面或文件夹的写入，在同一
  次提交、同一个日志事务里，把 `links` 表查出的引用文件里的路径改掉（只改
  路径部分，保留链接文字、`#锚点` 和其他内容；顺便给没带 `id` 的补上）。
  引用很多时（上限比如 500 个文件）照样一次做完，测耗时。远端空间同样一次
  提交推送。崩溃恢复：改链接属于这次移动的日志，恢复时一起做完。
- **外部改名的修复**：拉取后，按 `id` 发现目标换了位置，而引用文件里还是旧
  路径的，由服务自动改回（作为一次提交）；同一个 `id` 有两篇或找不到的不改，
  在 2.5 的校验页列出来。
- **保存时补 `id`**：保存一篇时，它的出链里能解析到页面、但没带 `id` 的，
  把 `id` 写进链接标题位置（原来有别的标题文字的不动）。
- **前端**：编辑器输入 `[[` 弹出页面选择（键盘可用），选中后插入
  `[标题](相对路径 "id")`；链接显示为普通链接，断链用不同样式，悬停显示
  目标当前标题；点击在应用里打开。右栏新增「反向链接」面板（按需加载）。
- **开销**：保存一篇只多解析它自己；改名、移动多改「链到它的那些文件」，
  从索引查，不扫磁盘；反向链接分页。5 万篇、单篇被 1 千篇引用时测改名的
  耗时。
- **服务改写链接不算冲突**：别人正开着、或服务端存着草稿的页面，如果只是
  因为服务改写了其中的链接路径（链到的页面改名或移动了、或它自己移动了）
  而落后，保存和草稿照常接受，把同样的改写做到这份文字上，不弹冲突、不把
  旧路径写回去。改写的记录存在状态目录（最多 2 万条，重启后仍在）。

2.4 已知问题，带到后面（都要好几个不常见的条件同时出现）：

- **崩溃后重做 `l` 记录不是幂等的**：被移动的页面自己的链接已经改写、但
  `ld` 还没写下时进程崩溃，下次启动会把已改写的内容按旧位置再解析一遍，
  没带 `id` 的相对链接会被改错（如 `A/B/A/B/y.md`）。远端空间里被撤销的
  移动、改名时试过又被占用的文件名，`l` 记录也会留着不关，下次启动时可能
  误改。要恰好在这几步之间崩溃才会出现。
- **改写一半时后台提交**：本地空间里 `writeEdits` 先把文件交给提交器再逐个
  写，若空闲提交恰好在写的过程中触发，一次改名会分成两个提交（内容不丢，
  只是历史不整齐）。要改很多文件、提交间隔又恰好到点时才会出现。
- **修复提交推送被拒**：拉取后服务做的链接修复提交，若推送前远端又有人推了
  新提交，下一轮会当作历史分叉，把这次修复另存为「救回的提交」并把远端标成
  出错，需要管理员看。要两边在几秒内先后推送才会出现。
- **保存途中又在打字**：保存请求发出后又继续打字，而服务端在这次保存上做了
  链接改写时，编辑器仍保留自己那份旧文字，下一次保存会按新版本号写回去，
  不再套用改写。带 `id` 的链接会在保存时按 `id` 修正；没带 `id` 的链接（在
  PetalBook 之外写的、或自己写了标题的）会写回旧路径，成为断链。
- **`Equivalent` 不检查改写链的终点**：改名后又改回来时，判断草稿是否和
  文件相同会多套用几步改写，结果是本可丢弃的草稿被留着；不丢内容。
- **改写记录的日志文件只在启动时压缩**：内存里最多 2 万条，但磁盘上的
  记录只在运行时追加，长时间运行、又有大量文件夹移动时会一直变大，启动时
  要全部读一遍。
- **一次改写超过 2 万个文件**：一次文件夹移动改写的文件超过 2 万个时，最早
  的几步会被挤出记录，这些文件上的草稿会显示为「落后」，和这次修复之前一样。

**2.5 模板和校验页**

- 模板是 `.petalbook/templates/` 下的普通页面，可带类型字段和正文；变量只
  支持日期和时间（`{{date}}`、`{{time}}`）。新建页面时选模板；文件夹可以
  设默认模板，快速记录也可以指定一个。
- **校验页**：列出空间里有问题的页面：没有或重复的 `id`、头部不是合法
  YAML、类型字段不符合 schema、断链、找不到的附件、同一文件夹标题重复。
  数据全部来自索引（`problems`、`props`、`links`），只在建索引时检查一次，
  打开校验页不扫磁盘。能直接修的给出按钮（补 `id`、清掉不在类型里的字段），
  其余点进去手修。

**2.6 API token 和 MCP**

- API token 按 Rackbook `internal/tokens` 的做法：只存哈希，限定到一个或
  几个空间，分只读和读写，有过期时间，可随时吊销。token 的权限不会超过
  签发人在这个空间的权限，签发人被移出或降级后立即生效（走 1.7 的成员缓存）。
- MCP 在 `/mcp`，复制 Rackbook 的 `mcpserver`、`oauthserver`、`mcpauth`。
  工具按 6.3 列的做：列出空间和文件夹、搜索、读页面、新建、修改、移动、
  打标签、看历史；加上 2.1 之后的按类型字段查询。列表和搜索走索引并分页，
  一次返回的条数和正文长度有上限，几万篇的空间也不会一次吐出全部。
- 写入走草稿和提交，作者是 token 的主人，提交信息末尾注明来自 MCP。
- 单用户模式没有账号：用命令行生成一个本地 token（`petalbook token`），
  MCP 用它连。
- 经 MCPHub 的接入放在这之后，单独确认 MCPHub 那边的令牌格式再做。

2.6 的约定（2026-11-23）：接口、工具和错误码先写进 `docs/api.md` 的「API tokens」
「OAuth for MCP clients」「MCP」三节和「Administration」里的「Machine access」，
前后端照它做。定下来的：

- **token**：`pbk_` 加 32 字节随机数（base62），状态库只存 SHA-256 和前 12 个
  字符；一个 token 限定 1～100 个空间（没有「全部空间」），`read` 或 `write`，
  默认 90 天过期（1～365 天，或不过期），每人最多 50 个有效的。吊销和过期的保留
  90 天再删，期间答 `token_revoked`／`token_expired`。
- **权限**：每次请求取主人现在在这个空间的权限（1.7 的成员缓存，不查库），和
  token 的 `access` 取交集；token 永远拿不到 `members`、`manage`，也不走管理员
  进入非成员空间的路。不在 token 里的空间答 `403 token_scope`，主人已不是成员的
  答 `404`，和网页一致；主人被停用答 `401 token_owner_disabled`。
- **查找的开销**：和会话一样，哈希后先查内存；没见过的哈希一次唯一索引查询，
  查不到的记 30 秒；内存里的记录最多 30 秒重读一次（命令行在另一个进程里吊销，
  30 秒内生效；经服务吊销立即生效）；最后使用时间每小时最多写一次。缓存命中的
  请求不查库。连续失败按客户端地址限速（每分钟 10 次）。
- **token 能用的接口**：空间内要 `read`／`write` 的路由、`GET /api/spaces`、
  `/api/meta`、`/api/session`（多一个 `token` 字段）和 `/mcp`；账号、用户、管理、
  token 自身的管理都不行，所以 token 不能再签 token。
- **单用户模式**：只有命令行 `petalbook token create|list|revoke`，直接读写状态库，
  服务运行时也能用；不带 token 的 `/api` 请求照旧，`/mcp` 必须带 token。OAuth 只在
  账号模式、且给了 `--public-url` 时有。
- **OAuth**：照搬 Rackbook 的授权服务（OAuth 2.1、只支持 S256 的 PKCE、RFC 8707、
  RFC 9207、客户端元数据文档优先、动态注册兜底、公开客户端），客户端和授权记录从
  JSON 文件改存状态库（SQLite 和 PostgreSQL 都测）。签名密钥也在状态库里，用
  服务器密钥（`secret.key`）封存，和别的凭据一样，不单独放文件；换了服务器密钥
  就打不开，服务不启动，而不是悄悄换一把把所有授权作废。scope 只有 `read`、`write`，
  空间在同意页上勾选（默认只勾个人空间）；一次授权之后的行为和同样范围的 token
  完全一样。访问令牌是 10 分钟的 ES256 JWT，只在本进程里验，验过的按哈希缓存到
  过期；刷新令牌每次轮换，60 秒内重发拿到同一个答复，之后重用就结束整个授权；
  90 天没刷新的授权失效。OAuth 访问令牌只能用在 `/mcp`（`/api` 答 `403 token_scope`）。
  机器访问里的 MCP 开关关掉时，授权服务的所有端点答 `404`，但授权记录保留，
  账号页和管理页仍可列出、吊销。主人被停用时刷新答 `invalid_grant`，授权保留，
  账号启用后继续有效。回调地址除 `https` 和本机回环的 `http` 外，也接受原生应用
  的私有协议（`cursor://` 之类，RFC 8252），Cursor、VS Code 要用。
  同一人同时等待决定的授权请求最多 20 个，全服务器最多 1000 个，超过的在错误页上
  显示 `temporarily_unavailable`（个人的答 `429`，全服务器的答 `503`）。
- **授权请求出错不再跳回客户端**（2.6 第二部分审查时改，**改了上面最初的约定，
  待所有者确认**）：最初约定 `client_id`、`redirect_uri` 以外的参数错误带 `error`
  跳回客户端的 `redirect_uri`；现在照 RFC 9700 第 4.11.2 节，用户同意之前的一切
  错误（`response_type`、`scope`、PKCE、`resource` 不对，请求过多）都只显示本服务器
  的错误页，不跳转，免得自行注册的客户端或任意元数据文档把本服务器当成开放跳转。
  只有在 `redirect_uri` 已核对、请求本身也合格之后，用户在同意页上拒绝时才带
  `access_denied` 跳回。
- **MCP 传输**：Streamable HTTP，无状态、只回 JSON（不开 SSE，没有 MCP 会话），
  空闲的客户端不占任何资源。`Origin` 检查照旧，防 DNS 重绑定。
- **工具**：`spaces_list`、`folders_list`、`tags_list`、`types_list`、
  `pages_search`、`pages_query`（2.1 的按类型字段过滤和排序，参数同 REST 列表）、
  `page_get`、`page_history`、`page_version`、`page_create`、`page_update`、
  `page_move`、`page_tag`。列表全部分页、走索引；搜索每次最多 50 条，查询最多
  200 条，条目不带正文、摘录最多 400 字；正文每次最多 128 KiB，按字节偏移续读；
  一个结果最多 1 MiB，超了答 `too_large` 并给出建议的条数。写入正文最多 1 MiB。
- **改正文**：`page_update` 可以整篇替换，也可以给一串「原文→新文」的精确替换
  （每段原文必须恰好出现一次），这样改一篇几十万字的长文不用把全文传来传去。
- **写入和草稿**：MCP 的写入和 REST 的保存一样（`baseRev` 冲突检查、记日志、
  提交、远端空间先推送再回答），**不经过主人的草稿**：一页一人只有一份草稿，
  MCP 写进去会和本人正在打的字互相覆盖，所以照 `PUT` 的规矩不碰草稿，草稿在网页
  里显示为落后。`page_tag`、`page_move` 的 `baseRev` 可选（加减标签、移动不会
  覆盖别人的文字）；`page_update` 必须带。`page_create` 可带 `requestId`，一小时内
  重发不会建两篇（只在内存里）。
- **提交信息**：作者是主人；MCP 的改动不和别的来源的改动合在一次提交里（来源
  变了就先提交，和 1.7 换作者一样），提交信息末尾加 trailer `Changed-via: MCP`；
  用 API token 走 `/api` 的改动加 `Changed-via: API token`。历史条目多一个
  `via` 字段（`mcp`／`token`）。trailer 里不写 token 的名字（名字是用户随便起的）。
- **管理员**：`/api/admin/access` 两个开关（token、MCP，默认都开；关掉不删数据），
  列出和吊销所有人的 token、授权。单用户模式用 `serve --mcp=false` 关 MCP。

已知问题（2.6 第一部分审查时记下，暂不处理）：

- PostgreSQL 上，同一人在同一时刻建两个 token，可能都通过「最多 50 个有效的」
  的检查，结果多出一两个。限制是先数后写，没有加锁；SQLite 只有一个写入者，
  不受影响。超出的不影响使用，吊销一个即可。
- 只要提交带 `Changed-via` trailer，历史里就会显示 `via`，包括从远端拉下来的
  提交：别人（或另一台 PetalBook）写的 trailer 在这里也会显示成 MCP 或 API token。
  `via` 只说明提交信息里写了什么，不是本服务器验证过的来源。

已知问题（2.6 第二部分，OAuth 服务审查时记下，暂不处理）：

- 授权码重放的检测有空档：第一次兑换还在保存授权记录时来的重放发现不了；兑换
  60 秒以后再来的重放也不再认作重放（只答 `invalid_grant`，不结束授权）。PKCE
  仍然保护着：没有 `code_verifier` 的人拿到授权码也换不到令牌。
- 被换掉的刷新令牌只记最近 8 个；更早的旧令牌再来时认不出是重用，只答
  `invalid_grant`，不会结束整个授权。
- 刷新用一把锁管所有授权（同一时刻只做一次刷新）。SQLite 本来就只有一个写入者，
  没有影响；PostgreSQL 上不同授权的刷新本可以并行，这把锁会限制吞吐。
- 60 秒宽限期内重发拿到同一个答复，这份答复只在内存里。PostgreSQL 上跑多个进程
  时，重试落到另一个进程就拿不到，答 `invalid_grant`（客户端要重新授权）。

- **`tools/list`**：凭据在自己的所有空间里都不能写时（`read` 的 token，或主人在
  这些空间都只是查看者），不列写工具；这一步查一次成员缓存，不查库。
- **上限**：结果在序列化后量一次，超过 1 MiB 就改答 `too_large`，列表类的附上
  `suggestedLimit`（按比例再打九折，且一定小于这次返回的条数，照着做一定有进展）。
  正文按字节偏移分块（128 KiB，在字符边界上截；头很大时按 1 MiB 减去其余部分
  剩下的空间截得更小，头本身就放不下任何正文时答 `too_large`）。写入的 `body` 最多 1 MiB；
  `edits` 只限制 `old` 和 `new` 加起来的大小，所以几十万字的长文也能改。
- **改正文**：新增 `space.Update`，在持有空间锁的那一次里读文件、交给调用方改、
  再写，所以 `edits` 总是对当前的文件做，没有「先读后写」之间的空档；`baseRev`
  冲突检查和 `Save` 一样（只有服务自己改写链接造成的差别不算冲突）。整篇换掉
  `body` 时用 `space.UpdateBody`：调用方的正文是按 `baseRev` 写的，服务之后做的
  链接改写也照 `Save` 那样做到这份正文上，结果和网页保存一样。
  `page_move` 的 `baseRev` 用新增的 `space.MoveIf`，`page_create`／`page_update`
  的其他字段用 `space.PatchMeta`（`PATCH …/props` 的规则，只是写整个头）。
  `drafts.Service.Write` 让这类写入和 `PUT` 一样排在同一页的草稿锁里，主人的草稿
  不动，网页里显示为落后；草稿写出来的内容正好和文件一样时才顺手删掉。
- **提交和来源**：作者是主人，`Changed-via: MCP` 在最后一行；MCP 的改动不和
  别的来源合在一起，但连着的几次 MCP 改动（同一个人）仍是一次提交，和同一个人
  连着打字一样。
- **`requestId`**：一小时、最多 1 万条、只在内存里；同一个键同时来两次，第二次
  等第一次做完再拿同一个答复（等待时跟着自己请求的 context 走）；失败或 panic
  的不记。重放之前照常检查一次权限，降级或移出的主人拿到的是拒绝。键里有凭据的 id，所以换一个 token
  不会拿到别人的答复。
- **单用户**：`serve --mcp=false` 关掉 `/mcp`（答 404）；账号模式下给了这个选项
  会报错，因为开关是管理员在界面里的。
- **测试**：第二部分的 `NewWithMCPStandIn`（让 `/api` 收 OAuth 访问令牌）去掉了，
  它的权限测试改成走 `/mcp`；`/api` 收到访问令牌仍然答 `403 token_scope`。

偏离或补充合同的地方：`types_list` 的结果是 `{"types": [...]}`（合同没写键名，
已补进 `docs/api.md`）；所有非 `POST` 的方法在看凭据之前就答 405；`folders_list`
的 `parent` 像网页一样不分大小写找文件夹；`page_update` 的 `edits` 的大小限制
改成只算 `old`＋`new`（合同只说了 `body`）。SDK 会把响应头 `Cache-Control` 写成
`no-cache, no-transform`，没有 `no-store`；结果里没有密钥，所以没有改它。

2.6 第三部分（MCP）的已知问题，暂不处理：

- `tags_list`、`folders_list` 每一页都重读整张表再切（和 `GET …/tags`、`…/tree`
  同样的一次查询，按标签数、文件夹数算，不按页数算）。实测 5 万页、5 千个标签／
  文件夹时，每次调用约 11 ms 和 6 ms。以后可以把分页挪进 SQL。
- 结果的结构化内容和文本各带一份 JSON，1 MiB 上限只管结构化内容，传输上约是它
  的两倍（文本再转义一次，最坏三倍），`docs/api.md` 已照此写明。
- `/oauth/*` 上「只允许 localhost」的拒绝和 404／405 的兜底仍用 API 的错误格式
  答复；跨站请求被拒的那个分支没有测试。
- 中间件把「`isError` 而没有结构化内容」都当成参数错误。现在只有 SDK 的校验会
  这样；将来 SDK 在别处返回这种结果会被误报成 `-32602`。
- `page_tag` 遇到 `tags` 里有非文字项（手改过的文件）时，写回会丢掉这些项；
  `tags: x`（单个文字）写回成列表。
- `requestId` 只在本进程内存里：PostgreSQL 上跑多个进程时，重试落到另一个进程
  就不认得，会建第二篇。
- `page_get` 按 `path` 找页面靠索引：在服务之外改过文件的，要重建索引后才找得到
  （按 `id` 取时会像 REST 一样先修索引）。
- 远端空间里一次写入可能重试几次，`page_update` 的改动函数因此会被调用多次
  （结果相同，只是重复算一遍）。

第二轮审查记下的已知问题，暂不处理：

- 重放 `requestId` 时，检查的是请求里写的那个空间，不是记下的那条答复所属的
  空间。重放只会还给同一个凭据它自己的那份答复，所以不是安全问题。
- 正文不到 1000 字节时，`page_get` 对剩余空间的估算可能差 3 个字节，所以头的
  大小几乎正好卡在上限上时，仍可能答 `too_large`。
- JSON-RPC 批量请求的响应走普通的 `json.Marshal`，`<>&` 各转义成 6 个字节。
  正常使用时不走这条路。

**2.8 passkey、SAML、多个登录提供方、登录验证码**

- passkey 和 SAML 用 authcore 的 `passkey`、`saml`。passkey 本地账号和外部
  账号都能绑；管理员可以要求某些人必须用 passkey。
- 把「一个 OIDC 提供方」改成「多个」：登录页每个一个按钮，账号的「安全」
  里逐个关联和解除；GitHub 登录单独写适配（见 1.7 的「多种登录方式」）。
- 同一个邮箱从不同提供方登录时不自动合并，规则同 1.7。
- **登录页、验证码、频率限制和锁定**（所有者 2026-11-22 提出：做成和
  KazuhaHub 的 Report Portal、Passwall-Sub-Panel 一样，包括 SSO）。两个项目
  的做法一致的地方照搬；不一致的地方以较新、也用 authcore 的 Report Portal
  为准，再加上 Passwall-Sub-Panel 的按 IP 每分钟请求数限制。
  - **登录页的四种状态**，由「登录方式」（`login_mode`）决定，只管页面怎么
    显示：
    1. `dual` 密码和 SSO（默认）：用户名、密码、（需要时）验证码、登录；下面
       「或者用以下方式登录」，每个提供方一个按钮「用 {名称} 登录」；忘记
       密码等链接。
    2. `sso_first` SSO 优先：提供方按钮在上，密码表单收起成一个链接「改用
       密码登录」，点了才展开。
    3. `sso_redirect` 只用 SSO（自动跳转）：只有一个提供方时直接跳过去，
       显示「正在前往 {名称}…」；有多个时不跳，列出按钮和「改用密码登录」。
       地址带 `?local=1` 或 SSO 失败回来带 `?sso_error=` 时不跳，免得失败后
       来回跳。
    4. `local_only` 只用密码：只有表单，没有 SSO 那一块。
    没有启用任何提供方时，不管设置成什么都按 `local_only` 显示。
  - **拒绝密码登录**（`sso_only`）是另一个开关，管服务端收不收密码：开了以后
    非管理员用密码登录一律拒绝（403 `local_login_refused`），管理员不受限，
    作为 SSO 坏了时的后门。保存时检查：开放注册时不能开；没有一个能用密码
    登录的管理员时不能开。这个开关不在公开接口里出现，免得别人知道哪些账号
    值得猜。没有提供方时它不起作用。
  - **提供方**可以有多个（OIDC 和 SAML），各有 `slug`、名称、图标；登录页读
    `GET /api/auth/providers`（提供方列表、`login_mode`、算好的 `local` 和
    `sso` 两个布尔值），点按钮是整页跳到 `/api/auth/{oidc|saml}/{slug}/start`。
    SSO 失败回到 `/login?sso_error=<码>`，页面显示对应的原因。
  - **验证码**用 authcore 的 `captcha`：自托管图片（默认，不出网）、
    Turnstile、reCAPTCHA、hCaptcha。
    - 用在哪：登录、接受邀请、首次设置管理员，以后的找回密码和公开注册；
      每一处单独开关。**SSO 不加验证码**（交给身份提供方）。
    - 什么时候要：每处可选「每次都要」或「错几次之后才要」（默认后者，
      默认 3 次，按 IP 和按用户名各算，任一到了就要）。
    - 页面向 `GET /api/captcha?ctx=login&account=<用户名>` 问要不要，要就同时
      拿到题目（图片），用户名改了再问一次。答错回 400，错误码
      `captcha_failed`，页面换一道题。验证码在算密码哈希之前查，答错不算
      密码错。第三方校验出错按失败处理（宁可拦下）。
    - 第三方的密钥加密存库，管理页只显示「已保存 · 更换」；换提供方时不沿用
      旧密钥；选第三方时站点密钥和密钥都必填。第三方校验核对返回的主机名
      是不是本服务的地址。
    - 题目存在内存里，最多一万道，5 分钟过期，每道只能答一次。
  - **频率限制和锁定**：
    - 按 IP 每分钟请求数（默认 10），用在登录、接受邀请、首次设置、取验证码、
      passkey 登录、SAML 回调上，超了 429，带 `Retry-After`。
    - 失败次数上限：在一个时间窗内（默认 15 分钟）按 IP、按用户名、按
      IP+用户名分别计数，上限默认 10；按 IP 的在算哈希之前查，按用户名的
      只在密码错了之后查，所以密码对的人不会被别人的失败挡住。超了 429
      `rate_limited`，带 `Retry-After`。现在的做法按这个改。
    - 锁定（默认关）：到了上限后锁一段时间（默认 15 分钟），范围可选
      「IP + 用户名」（默认，推荐）、「只按 IP」、「只按用户名」（会让别人
      能锁住某个账号，界面上要警告）。
    - 计数在内存里（单实例），重启清零；锁定和策略修改记审计日志。
  - **管理后台「安全」页**：登录（登录方式、拒绝密码登录，没有提供方时提示）、
    验证码（提供方、密钥、各处开关、触发方式和次数）、锁定（开关、时长、
    范围）、限制（每分钟请求数、失败上限、时间窗、会话时长）。这些设置存在
    状态库，改了立即生效，不用重启；现在只能用命令行参数配的 OIDC 也搬过来。
  - 单用户模式没有登录，以上都不涉及。

  - 管理员可以给个别用户或空间例外，也可以限制只在本地的空间的大小。
  - 允许哪些远端主机沿用现有的 `--remote-host`，搬到同一页里设置。
- **部分缓存**（4.5 的四步，只对跟随远端的空间）：
  1. 闲置的空间整个从本地删掉，索引留着，下次打开时再取回；
  2. 只取最近的历史，看历史时再按需向远端要更早的提交；
  3. 不预先取大文件的内容，附件在有人打开页面时才取，本地只留一个有上限
     的缓存；
  4. 连正文也按需取：用 Git 的部分克隆（`--filter=blob:none`）只拉提交和
     目录结构，不拉文件内容，本地只有索引和最近打开过的页面；打开一篇时
     再向远端取这一篇。所有者 2026-11-22 明确要这一步（「只拉取一部分，不用
     全部拉下来」）。
  管理员设一个本地磁盘预算，超了按最近最少用先腾空间。第 2 到 4 步要放宽
  受限 git 执行器允许的命令、要远端支持部分克隆（GitHub、GitLab 支持），
  做之前单独验证一次。
  - 第 4 步的代价要写明：没缓存的页面打开时多一次网络往返；远端连不上时
    这些页面打不开（界面上说清楚）；建索引和全文搜索仍要读全部正文，所以
    首次建索引时要把正文取一遍（可以流式取、建完就丢），之后靠增量同步，
    只取改过的文件。
- **独立的附件仓库**（3.4 的第 2 种后端）：文字一个仓库、附件另一个仓库，
  文字仓库保持小而快；页面提交前先确保它引用的附件已推送。和部分缓存一起
  做，附件仓库正是最该按需取的那一份。
- 这三样合起来的目标：服务器上每个空间只留索引、最近打开的内容和有上限的
  附件缓存，几万篇、很多用户时磁盘占用按「活跃的部分」算，而不是按全部。

## 14. 预留：公开发布

目前不做。目标是把指定页面公开发布，发布目标可选：

- **本服务直接提供**：只读页面，不需要登录，地址形如 `/p/<空间>/<slug>`。
- **GitHub Pages**：把选中的页面生成静态 HTML，推到一个公开仓库。

为此现在就要守住的约定：

- 头部保留 `publish` 字段，它不存在或为 `false` 时页面永不公开。
- 头部保留 `slug` 字段作为公开地址，缺省时由标题生成。
- 页面之间的链接是相对路径加目标的 ID（写法见 2.4），发布时按 ID 换成公开
  地址。指向未发布页面的链接降级为纯文字，不泄露标题以外的内容。
- 附件用相对路径引用，地址里不带令牌，发布时才能原样复制到公开目标。
- Markdown 转 HTML 的渲染要有一份不依赖编辑器的实现，服务端和静态生成共用。
- `space.yml` 里保留 `publish` 配置段，记录发布目标和主题。
- 发布是空间所有者的显式操作，并在界面上明确提示哪些页面当前是公开的。

## 15. 预留：表格

目前不做。计划是在文档之外，把**表格**作为空间里的另一种内容：一张完整的
电子表格（行、列、类型、排序筛选），不是文档正文里的 Markdown 表格，也不是
8.4 节里「把一个文件夹的页面排成表格」的那种视图。

方向（到时候再细化）：

- **一张表格是空间里的一个文件**，和页面一样跟着 Git 走：有历史、能对比、
  能在远端仓库里直接看。数据用按行的纯文本格式（倾向 CSV，一行一条记录，
  改一格只动一行），列的定义（名称、类型、选项、宽度、顺序）放在旁边的
  说明文件或文件头里，不混进数据。
- **和页面平级**：出现在文件夹树、列表、搜索、最近、标签里；有自己的 ID，
  地址和页面一样按 ID 定位；改名和移动不影响指向它的链接。
- **编辑走同一套保存流程**：草稿、提交、`baseRev` 冲突检查、远端同步。
  多人同时改一张表时，冲突按行、按格判断，而不是整个文件。
- **页面可以引用表格**（嵌入一个视图或链接到它），发布时遵守第 14 节同样的
  规则。

为此现在就要守住的约定：

- **「页面」不等于「空间里的内容」。** 接口和索引里凡是列出内容的地方
  （页面摘要、搜索、文件夹计数）都要能再加一个种类字段；现在不加，但前端
  不能假定列表里的每一项都是 Markdown 页面。页面摘要里已有的 `type` 是
  页面类型（第 3.3 节），不拿来表示种类。
- **ID 的格式和分配对所有种类通用**，一个空间里的 ID 在所有种类之间唯一。
- **地址按 ID，不按种类**：`/s/<空间>/p/<id>` 之后可以打开任何种类；不为
  表格另起一套地址。
- **`.md` 以外的文件现在只当附件**（`GET …/files/…` 原样给出）。将来某个
  扩展名成为表格后，它要像 `.md` 一样改由专门的接口读写；所以附件只放在
  `assets/` 下，不鼓励把数据文件散放在文件夹里并依赖它们被当作附件。
- **提交、日志、撤销、同步这一层只认路径，不认内容**（1.3 的 `txn` 已经是
  这样，1.4 的附件也走它）。新种类只需要在其上加自己的读写和索引。
- **保存流程里和正文格式有关的部分要留在边上**：草稿存的是「头部 + 正文」，
  这是页面的形状；状态机（版本号、`prev`、提交、冲突）本身不依赖它，将来
  换一种内容形状时应当能复用。
- `.petalbook/` 下保留 `tables/` 这个名字。
