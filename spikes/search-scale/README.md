# 搜索与列表的规模验证

第 0 期的验证：几万篇中文页面时，只靠本地 SQLite 索引够不够快，中文全文
搜索用哪种分词。

结论：**够快，不需要 Redis 或单独的搜索服务。全文索引用「逐字切分」方案，
不用三字符分词。**

## 测试条件

- 5 万篇页面，6220 万字，磁盘上 192 MB。70% 是短文案，25% 是笔记，5% 是
  五千到两万字的长文。
- Go 1.27，`modernc.org/sqlite`（纯 Go 驱动，正式实现打算用的那个）。
- Apple M5，本地 SSD。完整输出在 `results-50k.txt`。那次运行在项目改名之前，
  所以输出里的查询词写的是 `Petalbook`；搜索不区分大小写，结果不受影响。

语料是用约 300 个词随机拼出来的，所以常见词会命中绝大多数页面（「栀子」
命中 5 万篇里的 4.5 万篇）。这对排序是最坏情况，真实语料会比这快。

## 结果

| | 三字符分词 | 逐字切分 |
|---|---|---|
| 两个字的词（栀子、黄昏） | 查不了 | 105 到 222 ms |
| 一个字（海） | 查不了 | 172 ms |
| 常见的三字词（栀子花） | 30 ms | 190 ms |
| 少见的短语（只在 3 篇里） | 0.1 ms | 0.2 ms |
| 索引大小 | 405 MB，文本的 211% | 166 MB，文本的 87% |
| 从文件全量重建 | 1 分 50 秒 | 29 秒 |
| 保存一篇后更新索引 | 1.1 ms | 0.7 ms |

列表类查询两种方案相同，都不经过全文索引：

| 查询 | 耗时 |
|---|---|
| 某个文件夹的前 50 篇 | 0.1 ms |
| 某个标签的前 50 篇 | 2.9 ms |
| 全空间最近 50 篇 | 0.1 ms |
| 文件夹树和每个文件夹的篇数 | 7.9 ms |
| 所有标签和使用次数 | 15 ms |

对照：不建索引、直接扫描全部文件找一个两字词，要 9.9 秒。

## 为什么选逐字切分

中文的词大多是两个字，三字符分词查不了两个字和一个字的词，只能退回到
扫描全文，这一条就把它排除了。逐字切分的做法是入库前在每个汉字两边加
空格，让 SQLite 自带的分词器把每个字当成一个词；查询时把「栀子」变成短语
`"栀 子"`。它还更小、重建更快。

它慢的情况只有一种：查的词出现在上万篇里，要给上万个结果算相关度排序。
少见的词是亚毫秒级。

## 要知道的事

- **会跨标点匹配**。「栀子，花开了」会被「栀子花」搜到，因为分词器丢掉了
  标点。这次测试里因此多出约两成结果（语料是随机拼词，比例偏高）。修法
  是入库时把标点换成一个占位词，短语就跨不过去。这个修法还没测。
- **命中上万篇时的 200 ms** 可以再压：结果太多时改按更新时间排序，或只对
  前若干条算相关度。没做。
- **索引是「无内容」的**，只存倒排表不存原文。搜索结果里的上下文片段要从
  对应的 `.md` 文件现读，每次只读前 20 条，开销很小。
- 全量重建 29 秒只在索引丢失或格式升级时发生，平时每次保存只更新一篇。

## 运行

`-dir` 指定一个已存在的目录。程序只在其中新建的 `petalbook-search-scale`
子目录里工作，跑完删掉这个子目录，不会动 `-dir` 里的其他东西。

```bash
GOWORK=off go run . -n 50000 -dir /tmp
```
