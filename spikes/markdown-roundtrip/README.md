# Markdown 往返验证

第 0 期的验证：编辑器里的文档存成 Markdown 再读回来，会不会变。

结论：**编辑器用 Tiptap，Markdown 转换层自己用 remark 写**，不用官方的
`@tiptap/markdown`。

## 结果（2026-11-21，Tiptap 3.35）

文档优先测试，116 个用例。每个用例是一份「只用界面编辑会得到的文档」，
存成 Markdown 再读回，要求文档完全相同。

| 方案 | 通过 | 中文标点旁的强调 |
|---|---|---|
| Tiptap + 官方 `@tiptap/markdown` | 75/116 | 2/9 |
| 同上 + `marked-cjk-friendly` | 84/116 | 9/9 |
| Tiptap + remark 转换层（`lib/markdown.mjs`） | 113/116 | 9/9 |

这三行来自 `npm run compare`。

Markdown 优先测试，63 个用例（含 8 条仿照短文案写的示例），remark 转换层：49 个
零差异，10 个一次性规范化后稳定，0 个不稳定。另有 4 个被判为「有损」：
2 个是有意的改写（有序待办见「读入时改写的写法」，标题里的换行见「保存时
丢掉的看不见的东西」里的结构规则），2 个是判定器的误报，见下。

### 官方扩展的问题

加上中文插件后仍然失败的 32 个里，多数是保存后内容会变的真问题：

- 段落开头的 `# `、`- `、`1. `、`---` 不转义，重新打开变成标题、列表、分割线。
- 代码块里含 ` ``` ` 时围栏不加长，代码块被截断。
- 图片或链接地址含空格、括号时写出的语法不合法，图片失效。
- 链接标题含引号、空标题、相邻的两个列表、空代码块。
- `<`、`&` 写成 `&lt;`、`&amp;`，纯文本文件难读。
- 硬换行写成行尾两个空格，容易被别的编辑器删掉。

### remark 转换层剩下的 3 个

这 3 个登记在 `adapters/tiptap-remark.mjs` 的 `knownDifferences` 里。出现
名单之外的失败时 `npm test` 会报错退出。

| 用例 | 现象 | 说明 |
|---|---|---|
| 粗体头部带空格、粗体尾部带空格 | 空格被移到粗体外面 | 有意为之，肉眼看不出；Markdown 不允许强调符号贴着空格 |
| 正文里的裸网址 | 重新打开后变成可点击的链接 | 这是看得见的变化。编辑器输入时本来就会自动转链接，所以实际很少遇到；要改成把裸网址写成 `<网址>` |

### 保存时丢掉的看不见的东西

Markdown 存不下、人也看不见的内容，在保存时统一丢掉（`normalizeDoc`），
比较文档时先做这一步：

- 段落、标题、表格单元格末尾的空格和换行。
- 表格单元格开头的空格。
- 文档结尾的空段落（那只是光标停的地方）。空文档存成空文件。

全角空格不动，它是中文里看得见的缩进。

另有两条结构规则，是 Markdown 本身的限制：

- 表格必须有且只有第一行是表头。把表头行删掉后，下一行自动成为表头。
- 标题只能是一行。标题里的换行变成一个空格。

### 读入时改写的写法

编辑器里没有对应形式的 Markdown 写法，读入时改写一次。文字不变，但第二条
会丢掉编号：

- 引用式链接和图片（`[文字][1]` 加文末的 `[1]: 地址`）变成行内写法，定义
  行去掉。没有被用到的定义行也会去掉。
- 有序列表里的待办（`1. [ ] 一`）变成无序列表里的待办，编号丢失。
- 列表、标题的另一种写法（`*` 列表、下划线式标题）统一成一种。

### 范围

转换层只处理正文。文件头部（`id`、标题、标签）要先切下来单独解析，把整个
文件传进来会把头部读成分割线和标题。这部分还没写。

### 判定器误报的 2 个

- `约~10 个，价格 5~8 元`：marked 把单个 `~` 当删除线，我们的解析器关掉了
  这个行为（`singleTilde: false`），中文里的范围写法不会被误伤。
- `***粗斜体***` 被写成 `**_粗斜体_**`：等价写法，marked 在中文旁不认下划线。

## 转换层做了什么

- **中文友好的强调**：`**“引文”**。` 这类写法按 CommonMark 规范不算粗体。
  用 `remark-cjk-friendly` 系列插件解析和输出。代价见「要知道的事」。
- **不丢看不懂的内容**：原始 HTML 存成不可编辑的块，原样写回。脚注有专门
  的节点。
- **空段落**写成单独一行的 `<br>`。
- **硬换行**写成行尾反斜杠。
- **表格**不做列对齐填充，改一格只动一行；保留对齐方式。
- **行内代码**可以和粗体、链接共存（Tiptap 默认会把它们拆开）。
- **去掉下划线**：Markdown 没有对应语法。

踩到的一个坑：`remark-cjk-friendly` 的输出扩展会让待办列表的 `[ ]` 丢失，
需要在它之后重新注册 `gfmTaskListItemToMarkdown`。

## 浏览器里的实测（2026-11-21）

`browser/` 是一个最小的编辑器页面，右边实时显示会存进文件的 Markdown，
并在每次改动后自动做一次「存出再读回」的比对。用真实的键盘事件和粘贴在
浏览器里测过，所有情况下比对都一致。

| 测了什么 | 结果 |
|---|---|
| 输入快捷写法：`# `、`- `、`1. `、`[ ] `、`> `、三个反引号、`---` | 都生效 |
| Tab 缩进成子列表，Shift+Enter 段内换行 | 生效，写出的 Markdown 正确 |
| 空格后的 `**粗体**`、`*斜体*`、`` `代码` `` | 生效 |
| 选中「“引文在此”」按 Cmd+B、Cmd+I | 生效，重新打开后仍是粗斜体 |
| 粘贴网页或 Notion 式的富文本（标题、粗斜体、列表、引用、表格、图片） | 结构都保留；下划线和文字颜色按设计丢弃 |
| 粘贴 Word 式的富文本 | 正常 |
| 直接打出来的 `#`、`*`、`~`、`[` 等字面符号 | 保存时正确转义，重新打开还是原样 |

发现三个要在正式实现里处理的问题，都不是转换层的问题：

1. **紧跟汉字的 `**粗体**` 不会自动变粗体**。Tiptap 自带的规则要求 `**` 前面
   是空格或行首，中文里通常没有空格。用工具栏和快捷键不受影响；要让习惯
   打 Markdown 的人也顺手，需要自己写不要求空格的输入规则。
2. **粘贴多行纯文本时，每一行都变成独立的段落**，单个换行和空行的区别丢了。
   对诗行和分行的文案影响很大。要自定义：单个换行变成段内换行，空行才
   分段。
3. **粘贴 Markdown 源码不会变成排版后的内容**，`# 标题` 会原样留作文字
   （只有 `**粗体**` 会被识别）。要加一步：检测到粘贴的是 Markdown 就用
   转换层解析。

测试页有三种模式，默认是所见即所得：

- **所见即所得**：只有编辑器。
- **左右对照**：左边编辑器，右边 Markdown 原文，两边都能改，互相同步。
- **Markdown**：只有原文。

在原文一侧打的字会原样保留；一旦从可视一侧改动文档，原文就被重写成统一
写法（内容不变，比如 `*` 列表变成 `-`）。

没测到的：**中文输入法的组合输入**。自动化工具是直接插入文字，不经过
输入法。需要真人用拼音输入法在这个页面上试，重点看在列表、表格、行内
代码里组字时会不会吞字或错位。

启动这个页面：

```bash
npm run dev
```

然后打开 http://localhost:5183 。

## 性能

在 Node 加 jsdom 下测得，包含编辑器载入文档的时间：

| 文档大小 | 读入 | 存出 |
|---|---|---|
| 5 千字（长随笔） | 74 ms | 20 ms |
| 5 万字 | 547 ms | 152 ms |

自动保存要做防抖，不能每次按键都序列化。

## 要知道的事

- 无界面测试只验证转换层；浏览器里的结果见上一节，输入法还需要真人测。
- **示例文案是为测试编写的**，不是真实内容。真实的文案全量要等 Notion 导入器
  写出来后再跑一遍。
- **中文友好强调不是标准 CommonMark**。在 GitHub 网页上直接看原文件时，
  `**“引文”**。` 会显示出星号。我们自己的渲染（包括以后的公开发布）要用
  同一套规则。
- **服务端（Go）渲染 Markdown 时**用 goldmark 加 `goldmark-cjk-friendly`，
  已验证与前端一致，见 `../render-parity/`。
- 数学公式没有处理，`$…$` 目前当普通文字。
